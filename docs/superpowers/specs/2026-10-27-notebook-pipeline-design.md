# Перенос пайплайна из ноутбука в сервисы — дизайн

Дата: 2026-10-27. Источник: `MIEM_Last_Stable_Pipeline.ipynb` (корень проекта, вне git),
данные — `MIEM_HSE_knowledge_base.zip`, `HSE_Answers_RU.xlsx`.

## Зачем

Соседняя команда довела до рабочего состояния RAG-пайплайн в ноутбуке (гибридный поиск,
LLM-реранк, агрегация по документам, быстрые ответы). Он лучше отвечает на вопросы, чем
текущий векторный путь в `graph-rag-svc`. Задача — перенести его в сервисы так, чтобы
бизнес-логика жила в `ingest-worker` и `graph-rag-svc`, модели были вынесены, а ноутбук и
сервисы не расходились. Граф (GraphRAG) появится позже и накатится рядом.

## Цели

- `ingest-worker` разбирает документы по логике ноутбука (парсинг, чанкинг) и готовит данные
  для поиска: чанки, эмбеддинги, быстрые ответы, ссылки.
- `graph-rag-svc` отвечает по пайплайну ноутбука, читая индексы из базы, а не из zip.
- Эмбеддинги считает `embedding-svc` с моделью `intfloat/multilingual-e5-base`, локально.
- Все запросы к LLM идут через один прокси `llm-proxy` (nginx), который сам решает, куда их
  слать: на роутер (OpenAI-совместимый API; Polza/OpenRouter) или в Ollama. `graph-rag-svc`
  знает только адрес прокси и не знает ни ключа, ни провайдера, ни имени модели.
- Excel с быстрыми ответами и `all_links.txt` живут в базе.
- GraphRAG отключён: после правок работает только ветка ноутбука.

## Не цели

- GraphRAG не развиваем и не вызываем: `app/graph`, `app/ontology`, `cli/`, `api/graph_admin.py`,
  `app/retrieval/graph_retriever.py` остаются в репозитории, помечены как неработающие и ни
  откуда не импортируются при запуске. Прежний `judge`/`orchestrator`/`vector_retriever`
  удаляются, остаются в истории git. GraphRAG вернётся рядом, когда появится.
- Контейнеры `ollama`/`ollama-init` остаются в compose (профиль `llm`, по умолчанию выключен).
  Путь к Ollama заложен в прокси, но не запускается и не проверяется на живой модели.
- Оценка качества ответов и бенчмарк — отдельная задача.

## Анти-цели

- Нельзя ломать контракт `/generate`: сервис общий с Telegram-ботом соседней команды,
  режимы `stream`/`sync` сохраняются (README graph-rag-svc, §10–13).
- Нельзя оставить в базе векторы двух разных моделей: поиск тогда молча врёт.
- Ключ роутера не должен лежать нигде, кроме окружения `llm-proxy`.

## Решено владельцем

1. LLM — через прокси `llm-proxy`, который выбирает роутер или локальную модель. Ollama только резерв.
2. `ingest-worker`: меняем обработку документов; остальной код (очередь, повторы,
   `LISTEN/NOTIFY`, healthcheck, mTLS) разбираем по ходу работы.
3. `graph-rag-svc`: старый пайплайн вырезаем, подставляем ноутбучный.
4. `embedding-svc` остаётся и переходит на multilingual-e5-base (локально, GPU).
5. Индексы строятся из таблиц базы, не из zip. Excel и ссылки встраиваются в базу.

## Состав работ

### A. embedding-svc → multilingual-e5-base

- `EMBEDDER_MODEL_NAME=intfloat/multilingual-e5-base`, размерность **768**.
- E5 требует префиксов `query: ` / `passage: `. Сейчас сервис префиксов не добавляет, а
  ноутбук добавляет их на стороне вызывающего. Решение: в `/embed` добавить необязательное
  поле `kind` (`passage` по умолчанию, `query`), префикс ставит сервис. Так правило живёт в
  одном месте, и `ingest-worker` с `graph-rag-svc` не могут разойтись.
- Смена модели требует пересоздания колонок `VECTOR(1024)` → `VECTOR(768)`
  (`library.chunk_embeddings.embedding` и новые таблицы), `EMBEDDING_DIM=768` в `.env`/compose
  и пересчёта всех чанков. Стартовые проверки размерности в `ingest-worker` и `graph-rag-svc`
  ловят рассинхрон.
- `graph.entities.name_embedding` остаётся `VECTOR(1024)` и не пересчитывается: GraphRAG
  отключён, граф не читается. Проверка размерности в `graph-rag-svc` эту колонку больше не
  проверяет. При возврате GraphRAG колонку и граф пересчитывают вместе с соседней командой.

### B. База: быстрые ответы и ссылки

Разобранная структура источников:

- `HSE_Answers_RU.xlsx`: один лист «Ответы», 122 строки, **три колонки** — «Основной вопрос»,
  «Ответ на русском», «Варианты вопроса на русском» (варианты разделены переводом строки).
  Колонок `№`, `ID`, `Термин`, `Источник` и английских, на которые рассчитан ноутбук, в
  файле нет.
- `all_links.txt`: 92 строки вида «описание-ключевые слова. URL». Одна ссылка начинается с
  `http://` (общежития), остальные с `https://`.

Новые таблицы в схеме `library` (миграция 011):

- `quick_answers(id, question, answer, source, is_active, created_at, updated_at)`.
- `quick_answer_variants(id, quick_answer_id → quick_answers ON DELETE CASCADE, text,
  embedding VECTOR(768))`: одна строка на основной вопрос и каждый вариант.
- `links(id, description, url, embedding VECTOR(768), is_active, ...)`.

Загрузка: администратор импортирует Excel и список ссылок через `db-svc` (там уже есть
CSV/HTML-импорт), строки попадают в таблицы без эмбеддингов, `ingest-worker` досчитывает
эмбеддинги по тому же механизму очереди, что и для чанков. Бизнес-логика эмбеддинга остаётся
в воркере.

### C. ingest-worker

- Заменить `parsers.py` и `chunker.py` на логику ноутбука: блоки `section/kind/text`,
  таблицы DOCX строками «Заголовок: значение», структурный чанкинг до 1600 символов,
  overlap по последнему абзацу (до 350), минимум 80 символов, очистка шума.
- В `library.chunks` пишется `section_path`; поля `title`, `category` берутся из
  `library.documents`/тем, потому что ноутбук подмешивает их в текст для эмбеддинга и BM25
  (`passage: Название / Категория / Раздел / Текст`).
- Эмбеддинги чанков — через `embedding-svc`, `kind=passage`.
- Добавить обработку `quick_answer_variants` и `links` (пункт B).
- Остальной код `main.py` (модели, очередь, повторы, `LISTEN/NOTIFY`, mTLS) — разбор по ходу.

### D. graph-rag-svc

- Удалить `judge`, `vector_retriever`, `orchestrator`, `context_assembler`; `graph_retriever`
  оставить с пометкой «не работает, не вызывается». Подставить модуль пайплайна ноутбука
  (`app/pipeline/`):
  1. быстрый ответ: гибридный поиск по `quick_answer_variants` (dense + BM25, RRF с весами
     1.5/1.0, пороги RRF ≥ 0.04 и косинус ≥ 0.83); если прошёл — отдать готовый ответ без LLM;
  2. переписывание вопроса с историей (если история есть);
  3. кандидаты: dense (pgvector) top-60 + BM25 top-60, RRF 1.0/0.9, top-40;
  4. реранк одним вызовом LLM (первые 28, текст до 1100 символов, top-18);
  5. агрегация по документам (веса 1/0.55/0.30/0.15), выбор 1–2 документов, до 9 чанков с
     соседями `±1`, контекст до 18000 символов;
  6. ссылки: top-3 из `links`, порог 0.75;
  7. ответ LLM (температура 0.3, 1100 токенов) с guardrails и правилом языка.
- BM25 строится при старте из `library.chunks` (+ title/category/section) и
  перестраивается, когда меняется набор чанков.
- Контракт `/generate`, очередь, sinks, аналитика (`rag.*`) сохраняются.
- LLM-вызовы (реранк, переписывание, ответ) идут клиентом `openai` на `llm-proxy`
  (`LLM_BASE_URL`, `model: "default"`). Ключа и выбора провайдера в `graph-rag-svc` больше нет:
  `llm_backends.py` сводится к одному OpenAI-совместимому клиенту, `requirements-local.txt` и
  `WITH_LOCAL_LLM` удаляются.
- GraphRAG отключается: из `main.py` убираются `graph_admin_router` и `release_orphaned_runs`,
  `verify_embedding_setup` проверяет только `library.*`, `graph_build_api_enabled=False`.
  Модули графа получают в начале файла пометку `DISABLED`. В `db-svc` маршруты курирования
  графа отключаются так же (они ходят в `graph-rag-svc`, где их больше нет).

### E. llm-proxy (новый контейнер)

- nginx (`nginx:1.27-alpine`, модуль njs есть в образе). Настройки живут в файле
  `/etc/llm-proxy/config.json` на именованном томе, а не в переменных окружения:
  `{"mode": "router"|"ollama", "router": {"url": ..., "model": ...}, "ollama": {"url": ..., "model": ...}}`.
- **Настройки подхватываются на лету.** njs читает файл на каждом запросе (или по `mtime`), поэтому
  смена режима, модели или адреса роутера действует со следующего запроса, без перезапуска и
  `nginx -s reload`. Битый или неполный файл не ломает работу: используется последняя
  корректная конфигурация, ошибка пишется в лог. Если корректной конфигурации не было с
  самого старта, LLM-запросы получают 503.
- Ключ роутера (`ROUTER_KEY`) в файл не кладётся: он остаётся секретом в окружении прокси.
- njs выбирает upstream по `mode`, подменяет `model` в теле на модель режима и заменяет
  `Authorization`; остальное тело не меняет. Вызывающий передаёт `model: "default"`.
  Потоковый ответ (SSE) идёт без буферизации.
- Права вызова — по образцу `infra/mtls/*.conf`: клиентский сертификат, пропускается только CN
  `graph-rag-svc` и только `POST /v1/chat/completions`. В режиме `ollama` прокси ходит к
  Ollama по mTLS (`ollama.conf` разрешает CN `llm-proxy`). Ключ и заголовок `Authorization`
  в логи не попадают.
- Путь `ollama` проверяется только на заглушке upstream; настоящую модель не поднимаем.
- Запись в `config.json` пока никто не делает (файл создаётся по умолчанию при первом старте
  тома). Позже его будет менять админка `db-svc` (атомарно: запись во временный файл и
  `rename`); том для этого уже общий.

### F. Страница настроек в админке

- Сейчас только чтение, без переключателей: текстом показывает режим LLM (роутер/Ollama),
  имя модели, модель эмбеддингов с размерностью и что GraphRAG отключён.
- `db-svc` читает тот же `config.json` (том подключён только на чтение), так что страница
  показывает реально действующие настройки, а не копию из переменных. `GET /api/db/settings/project`
  возвращает значения без ключей; раздел добавляется в `app/static/index.html`.
- Переключение из админки — следующий шаг (см. выше): том станет доступен `db-svc` на запись.

### G. compose и конфигурация

- Добавить `llm-proxy` в compose; `graph-rag-svc` зависит от него, а не от Ollama.
- Профиль `llm` (ollama) остаётся выключенным; `ollama.conf` дополнительно пускает CN `llm-proxy`.
- Ключ роутера хранится только в окружении `llm-proxy` (`ROUTER_KEY`, не в git); режим, модели и адреса — в `config.json`.

## Расхождения ноутбука с реальными данными (исправляем при переносе)

1. Ноутбук ждёт колонки `№`, `ID`, `Термин`, `Источник`, `Варианты вопроса (RU)`,
   `Question variants (EN)`, `Answer in English`. В `HSE_Answers_RU.xlsx` колонка вариантов
   называется «Варианты вопроса на русском», остальных нет — варианты в ноутбуке молча
   отбрасываются. Мы читаем реальные колонки.
2. Ссылка с `http://` пропускается фильтром `"https://" in line`.
3. Глобальная `bm25` для чанков перезаписывается индексом быстрых ответов (ячейка 32).
   В сервисе индексы раздельные.
4. В `FINAL_SYSTEM` русский/английский язык определяется дважды (в промпте и в ячейке 36);
   оставляем одно правило.
5. Описание в заголовке ноутбука говорит о 103 документах; в архиве 205 (166 docx, 39 txt, 2 pdf
   по расширениям; категории «Общие документы» 187, «Учебный процесс» 18).

## Мои решения (проверьте)

- Подмену `model` делает njs внутри прокси; настройки хранятся в файле на общем томе (мой выбор,
  чтобы админка могла менять их без перезапусков).
- Прокси — nginx в compose, а не отдельный Python-сервис и не репозиторий: конфигурация лежит в
  `main/infra/llm-proxy`.
- Быстрый ответ отдаётся без вызова LLM — как задумано в ноутбуке (пороги из ячейки 33).
- `kind` в `/embed` — поле запроса, а не отдельный эндпоинт.
- Excel/ссылки загружаются через админку `db-svc`, а не автоматом из репозитория.
- Нумерация миграции 011 — следующая после 010.
