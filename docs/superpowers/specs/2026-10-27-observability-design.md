# Наблюдаемость: метрики, логи, дашборды (IVHR-84, IVHR-85)

## Зачем

Сейчас о состоянии стека можно судить только по `docker logs` на каждом контейнере. Метрик нет
нигде (в коде нет ни `/metrics`, ни `prometheus`), логи не собраны, состояние машины не видно.
Нужно в одном месте смотреть: живы ли сервисы, как ведёт себя продукт (чат, поиск, загрузка
документов) и что происходит на хосте, а по логам находить причину сбоя.

## Цели

- Prometheus собирает метрики сервисов, хранилищ и хоста; Loki хранит логи всех контейнеров;
  Grafana показывает и то и другое.
- Сервисы отдают технические (HTTP) и бизнес-метрики; набор метрик согласован заранее (ниже).
- Сбор работает и в простом режиме (`docker-compose.yml`), и за mTLS (`docker-compose.mtls.yml`):
  у Prometheus свой сертификат, прокси сервисов пускают его только на `/metrics`.
- Несколько дашбордов, между которыми распределены все метрики; всё поднимается из файлов
  (datasource и дашборды в репозитории), руками в Grafana ничего настраивать не надо.

## Не цели

- Алерты (Alertmanager) и уведомления: в первой итерации нет.
- Трассировка (Tempo/OTel) и Kubernetes-манифесты.
- Метрики crawler-svc и frontend (нет прав на запись); логи crawler-svc собираются как у всех.
- Хранение метрик и логов дольше срока из раздела «Решения».

## Что решено вместе с владельцем

- Стек: Prometheus + Loki + Grafana, плюс node-exporter для состояния машины.
- Агент логов для Loki выбираем сами.
- Бизнес-метрик в сервисах сейчас нет: их нужно добавить, набор определяем в этом документе.
- Prometheus получает собственный сертификат во внутреннем CA.
- В Grafana несколько дашбордов, все метрики разнесены по ним.

## Решения (мои, можно оспорить)

- **Агент логов: Grafana Alloy**, не Promtail (Promtail устарел и заменён Alloy). Читает логи
  контейнеров через Docker (`/var/run/docker.sock`, только чтение), метка `service` берётся из
  имени compose-сервиса.
- **Отдельный оверлей `docker-compose.observability.yml`** и профиль `observability`: обычный
  запуск стека не меняется и не тратит память. Подключается так же, как pki и mtls, через
  `COMPOSE_FILE`.
- **cAdvisor** добавляем к node-exporter: без него на дашборде нет CPU и памяти по контейнерам.
- **Экспортеры хранилищ**: redis_exporter, postgres_exporter, у MinIO собственные метрики
  (`/minio/v2/metrics/cluster`), у nginx экспортёр по `stub_status`.
- **GPU (dcgm-exporter) в первую итерацию не входит**: нужен `nvidia` runtime в ещё одном
  контейнере. Сделаем, если понадобится видеть загрузку GPU под `embedding-svc`.
- **Сроки хранения**: метрики 15 дней, логи 14 дней, Loki в режиме одного бинарника с хранением
  на диске (том).
- **Библиотеки в сервисах**: `prometheus-client` и `prometheus-fastapi-instrumentator` для
  HTTP-метрик; бизнес-метрики пишутся в коде сервисов. Все свои метрики с префиксом
  `pochemuchnik_`.
- **Доступ к Grafana: порт только на `127.0.0.1`** (без nginx и без выхода наружу). Вход
  паролем из `.env`. Оговорено в «Вопросах владельцу».

## Как это встраивается в mTLS

В режиме mTLS приложение слушает только `127.0.0.1` внутри сетевого пространства своего
прокси-сайдкара, и снаружи достучаться можно лишь до `:8443` с клиентским сертификатом.
Поэтому:

1. Prometheus получает сертификат с CN `prometheus` (`scripts/pki/enroll.sh prometheus` и
   контейнер-обновлятель, как у остальных).
2. В `infra/mtls/<сервис>.conf` каждого сервиса добавляется правило: `prometheus` может только
   `GET /metrics`, остальное ему закрыто.
3. Для двух режимов нужны два набора scrape-целей (http на порт приложения без mTLS и https на
   `:8443` с сертификатом при mTLS). Как их переключать (две конфигурации или подстановка
   переменных), решает исполнитель.
4. redis_exporter ходит в Redis по `rediss://` как ACL-пользователь с минимальными правами
   (`scripts/gen_redis_acl.py` дополняется пользователем `prometheus`); postgres_exporter входит
   по клиентскому сертификату с ролью, которой достаточно `pg_monitor`.

## Метрики по сервисам (предложение, нужно согласовать)

Для всех HTTP-сервисов (auth, chat, library, db, graph-rag, embedding): число запросов, задержка
и число запросов в обработке по шаблону маршрута и коду ответа (даёт instrumentator).

| Сервис | Бизнес-метрики |
| :-- | :-- |
| auth-svc | регистрации; входы по результату; обновления токена по результату; письма по виду и результату; админ-сессии |
| chat-svc | активные WebSocket-соединения и их число за всё время; сообщения по роли; время до первого токена и полное время ответа; сбои генерации по причине; оценки (фидбэк) по значению; попадания и промахи кэша Redis (профиль, сессия) |
| graph-rag-svc | запросы `/generate` по режиму; решение judge (граф или вектор); длительность этапов (поиск, генерация) отдельно; число чанков в контексте; ответы с пустым контекстом; ошибки LLM |
| embedding-svc | запросы `/embed`; размер пакета; время эмбеддинга |
| library-svc | запросы предпросмотра по режиму; попадания и промахи кэша конвертации (IVHR-20), вытеснения, время конвертации LibreOffice; скачивания; число документов по статусу |
| ingest-worker | глубина очереди; обработанные документы по результату; длительность обработки; созданные чанки; ошибки по типу |
| db-svc | действия админов по виду; импорты по виду и результату; размер корпуса и графа (документы, чанки, узлы, рёбра) |

Хранилища и хост дают готовые экспортеры (Postgres, Redis, MinIO, nginx, node-exporter, cAdvisor).

## Дашборды Grafana

1. **Обзор стека**: какие сервисы живы, доля ошибок и задержка по сервисам.
2. **Хост и контейнеры**: CPU, память, диск, сеть машины и контейнеров.
3. **Чат и RAG**: соединения, сообщения, время ответа, решения judge, пустой контекст, фидбэк.
4. **Документы и ingest**: очередь, обработка, чанки, эмбеддинги, предпросмотр и его кэш.
5. **Пользователи и auth**: регистрации, входы, письма, админ-действия.
6. **Хранилища**: Postgres, Redis, MinIO, nginx.
7. **Логи**: ошибки по сервисам, поиск по тексту и по `service` (источник Loki).

## Порядок работ

1. Оверлей с Prometheus, Loki, Alloy, Grafana, node-exporter, cAdvisor; datasource и пустой
   каталог дашбордов; проверка в простом режиме.
2. Сертификат Prometheus и правила `prometheus -> /metrics` в прокси; проверка за mTLS.
3. HTTP-метрики во всех сервисах.
4. Бизнес-метрики по сервисам (по сервису отдельным коммитом в его сабмодуле).
5. Экспортеры хранилищ и их доступы (ACL Redis, роль Postgres, метрики MinIO).
6. Дашборды.
7. Документация (`deploy.md`, README сервисов) и проверки (по образцу `infra/mtls/tests`).

Первые два и пятый пункты относятся к IVHR-84 (контейнеры), остальное к IVHR-85 (сбор логов и
метрик); границу уточним при разбиении коммитов.

## Ограничения

- Работа идёт в ветке `dev`; изменения в сервисах коммитятся в их сабмодулях, затем отдельный
  коммит в `main` с обновлением ссылки. `crawler-svc` и `frontend` не трогаем.
- При проверках не запускать профиль `llm` и `embedding-svc`; сервисы проверять на одноразовых
  контейнерах.
- Метрики не должны содержать идентификаторов пользователей, текста вопросов и ответов; метки с
  неограниченным числом значений (id пользователя, id документа, путь с id) запрещены.
