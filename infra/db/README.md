# База данных: схема, роли, права

```
infra/db/
├── init/
│   ├── init.sql              схемы и таблицы; исполняется на ПУСТОМ томе (docker-entrypoint-initdb.d)
│   └── roles/                роли и права — единственное место, где они описаны
│       ├── vars.sql          имена ролей и пароли из окружения контейнера postgres (\getenv)
│       ├── create_roles.sql  создаёт роли, синхронизирует атрибуты и пароли
│       ├── grants.sql        сбрасывает и заново выдаёт все права
│       └── sync.sql          create_roles + grants одним запуском (для существующей базы)
├── migrations/               для уже поднятых баз; 008 — роли и журнал действий
└── tests/check_roles.sh      проверка прав: что сервисам можно и, главное, нельзя
```

## Модель ролей

Раньше каждый сервис получал полный CRUD на «свою» схему, а db-svc подключался
суперпользователем контейнера (`POSTGRES_ADMIN_USER`), он же был владельцем всех объектов.
Теперь:

| Роль | Вход | Назначение |
| :-- | :-- | :-- |
| `POSTGRES_ADMIN_USER` | да | Суперпользователь контейнера. Только инициализация, миграции и оператор; **ни один сервис под ним не подключается** |
| `app_owner` | нет | Владелец схем и всех объектов. DDL и миграции выполняются под `SET ROLE app_owner` |
| `<схема>_ro`, `<схема>_rw` | нет | Группы прав на схему (`core`, `auth`, `chat`, `library`, `graph`, `rag`): чтение / чтение и запись. `_rw` включает `_ro` |
| `auth_user`, `chat_user`, `library_user`, `ingest_user`, `graph_user`, `dbsvc_user` | да | По одной на процесс. Не суперпользователи, без DDL, с лимитом соединений. Права — членством в группах и точечными `GRANT` |

Имена LOGIN-ролей и их пароли задаются в корневом `.env` (`AUTH_DB_USER`, `AUTH_DB_PASSWORD`,
…, `INGEST_DB_*`, `DBSVC_DB_*`) и попадают в SQL из окружения контейнера postgres. Паролей в SQL
больше нет; без непустых паролей инициализация останавливается с понятной ошибкой.

### Что кому можно

| Роль | Доступ |
| :-- | :-- |
| `auth_user` | `auth.*` — чтение и запись; `core` — чтение |
| `chat_user` | `chat.*` — чтение и запись; `core` — чтение. `auth.users` не видит (ссылки на неё проверяет БД от имени владельца) |
| `library_user` | **только чтение**: `library.topics`, `documents`, `document_files`, `document_relations`; `core` — чтение. library-svc ничего не пишет |
| `ingest_user` | `library.documents` — чтение и `UPDATE` только колонок очереди (`ingest_status`, `ingest_attempts`, `ingest_started_at`, `indexed_at`, `ingest_error`, `ingest_next_attempt_at`); `document_files` — чтение; `chunks`, `chunk_embeddings` — чтение, вставка, удаление; `core` — чтение. Менять заголовки и каталог не может |
| `graph_user` | `graph.*` — чтение и запись; `rag.*` — чтение и вставка; `library` — чтение; `core` — чтение. Библиотека открыта целиком потому, что той же ролью подключается экземпляр соседней команды (см. `graph-rag-svc/README.md`, §12.1); сузить можно после согласования с ними |
| `dbsvc_user` | `core`, `library` — запись (и `TRUNCATE` для CSV-импорта в режиме замены); `graph`, `chat`, `rag` — **только чтение** (граф правится через graph-rag-svc); `auth.users` — все колонки кроме `password_hash`, изменение и удаление, без вставки; `auth.user_profiles` — запись; таблицы токенов — чтение без `token_hash`; `public.dbsvc_jobs` — запись; `audit.db_actions` — только `INSERT` и `SELECT` |

Колонки `password_hash` и `token_hash` недоступны админке: хеши ей не нужны, а утечка через
неё стоила бы больше, чем неудобство.

## Как применяется

**Новый том.** Ничего делать не нужно: `init.sql` создаёт роли (`create_roles.sql`), затем
схемы и таблицы от имени `app_owner`, затем выдаёт права (`grants.sql`).

**Существующая база.** Один раз применить миграцию 008 (после обновления корневого `.env` и
пересоздания контейнера postgres, чтобы в нём были новые переменные):

```bash
docker compose up -d postgres
docker compose exec -T postgres psql -U "$POSTGRES_ADMIN_USER" -d "$POSTGRES_DB" \
    -v ON_ERROR_STOP=1 < infra/db/migrations/008_roles_and_audit.sql
```

Миграция передаёт владение объектами `app_owner`, создаёт `audit.db_actions` и
`public.dbsvc_jobs`, обновляет пароли ролей и пересобирает права. Данные не затрагиваются,
повторный запуск безопасен. После неё пересоздайте сервисы (`docker compose up -d`): `ingest-worker`
и `db-svc` переходят на свои новые роли. Пока миграция не применена, новый `db-svc` не
сможет подключиться (роли `dbsvc_user` ещё нет), а у `library_user` и `graph_user` после
неё остаётся ровно то, что описано выше.

**Сменили пароль в `.env`.** Init-скрипты исполняются только на пустом томе, поэтому пароль в
самой базе сам не поменяется. Пересоздайте postgres и выполните:

```bash
docker compose exec -T postgres psql -U "$POSTGRES_ADMIN_USER" -d "$POSTGRES_DB" \
    -v ON_ERROR_STOP=1 -f /docker-entrypoint-initdb.d/roles/sync.sql
```

`sync.sql` заодно пересобирает права, так что это же — способ привести базу к `grants.sql`
после его правки.

## Новые таблицы и миграции

Права на новые объекты выдаются автоматически, но только если их создал `app_owner`
(`ALTER DEFAULT PRIVILEGES FOR ROLE app_owner`). Поэтому миграции пишутся так:

```sql
SET ROLE app_owner;
-- CREATE TABLE ...
RESET ROLE;
```

Таблица, созданная суперпользователем, останется без прав у всех сервисов. Что именно нужно
конкретному сервису (например, `library_user` и `ingest_user` получают права на таблицы
точечно), задаётся в `roles/grants.sql`; после его правки запустите `sync.sql`.

## Журнал действий администратора

`audit.db_actions` заполняет db-svc: каждое изменение строки (с прежним и новым значением),
CSV- и dataset-импорт, загрузка, выдача ссылки на загрузку и удаление файла в MinIO, операции
с графом, отмена задач, выгрузки. Запись строки данных идёт в той же транзакции, что и
изменение: нет записи — нет и изменения.

```sql
SELECT occurred_at, actor_type, actor_user_id, action, target_schema, target_table, target_pk, success
FROM audit.db_actions ORDER BY id DESC LIMIT 50;
```

`actor_type`: `user` — администратор из админ-сессии (известен `actor_user_id`), `token` —
вызов по общему Bearer-токену (личность неизвестна), `anonymous` — авторизация отключена
явным `DBSVC_ALLOW_NO_AUTH`. У db-svc на таблицу только `INSERT` и `SELECT`, а триггер
запрещает `UPDATE`, `DELETE` и `TRUNCATE` даже владельцу, пока он не отключит триггер
осознанно. Чистку и ротацию журнала нужно делать отдельным ручным шагом под суперпользователем.

## Проверка

```bash
infra/db/tests/check_roles.sh            # по умолчанию контейнер postgres
infra/db/tests/check_roles.sh pgtest     # любой другой контейнер
```

Скрипт выполняет проверки под `SET LOCAL ROLE` и откатывает их, данные не меняются. Он
проверяет, что сервисам нельзя лишнее (чужие схемы, DDL, хеши, правка журнала), что нужное
работает (в том числе очередь ingest-worker и CSV-замена), что объекты принадлежат
`app_owner`, а новые таблицы получают права по группам, и что вход по паролю работает. Для
db-svc есть сквозная проверка приложения на живой базе: `services/db-svc/tests/test_audit.py`.

## Что осталось и почему

- **Пароли.** Роли сервисов пока входят по паролю. Вход по клиентскому сертификату
  (`hostssl ... cert`, соответствие CN→роль через `pg_ident`) планируется вместе со step-ca и
  уберёт пароли совсем.
- **`pg_hba` образа** разрешает `trust` на loopback и сокете внутри самого контейнера postgres.
  Снаружи (из сети compose) пароль проверяется; сужение `pg_hba` — часть того же шага с TLS.
- **Построчная защита (RLS) для `chat`** не делалась. Она защищает от забытого `WHERE user_id`
  в коде chat-svc, но не от скомпрометированного chat-svc (он сам выставит нужного
  пользователя), а требует правок транзакций сервиса. Вернёмся к вопросу после переезда.
- **Таймауты запросов** на роль не заданы намеренно: ingest-worker держит транзакцию открытой
  на время парсинга и эмбеддинга документа, и общий `idle_in_transaction_session_timeout` оборвал бы её.
- **`crawler-svc`** подключается к базе своим URL (чужой репозиторий, вне compose) и в этой
  модели не учтён; для него потребуется отдельная роль с правами на `library.documents`.
