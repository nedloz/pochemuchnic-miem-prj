# llm-proxy

Единственная точка, через которую `graph-rag-svc` обращается к LLM. Сервис шлёт обычный
OpenAI-совместимый запрос на `http://llm-proxy:8080/v1/chat/completions` с `model: "default"` и
фиктивным ключом, а прокси решает, куда его отправить: во внешний роутер (с ключом) или в Ollama
(без ключа), и подставляет модель выбранного режима. Это nginx (`nginx:1.27-alpine`) с модулем
njs, отдельного кода и образа нет: всё лежит в этом каталоге и монтируется в контейнер.

## Настройки: `config.json`

Файл `/etc/llm-proxy/config.json` на именованном томе `llm_proxy_config`:

```json
{
  "mode": "router",
  "router": {"url": "https://api.polza.ai/v1", "model": "qwen/qwen3.5-9b"},
  "ollama": {"url": "https://ollama:8443/v1", "model": ""}
}
```

- `mode` — `router` или `ollama`; `url` — базовый адрес OpenAI-совместимого API режима (запрос уйдёт
  на `<url>/chat/completions`, лишний `/` в конце не мешает); `model` — модель, которая подставится
  в тело вместо присланной.
- Формат файла и имя тома — контракт: позже файл будет менять админка `db-svc`, а страница
  настроек (`GET /api/db/settings/project`) уже читает его с того же тома.
- На пустом томе файл создаёт `entrypoint.sh` из `config.default.json` (значения выше).
  Существующий файл при старте не трогается, даже некорректный.

**Настройки подхватываются на лету.** Файл читается заново на каждом запросе, поэтому смена
режима, модели или адреса роутера действует со следующего запроса — без перезапуска контейнера и
без `nginx -s reload`. Записывать файл нужно атомарно — во временный файл рядом и `mv` (rename):
так прокси никогда не прочитает половину записи.

```bash
docker exec -i llm-proxy sh -c 'cat > /etc/llm-proxy/config.json.tmp && mv /etc/llm-proxy/config.json.tmp /etc/llm-proxy/config.json' <<'EOF'
{"mode": "ollama", "router": {"url": "https://api.polza.ai/v1", "model": "qwen/qwen3.5-9b"},
 "ollama": {"url": "http://ollama:11434/v1", "model": "mistral"}}
EOF
```

**Некорректный файл не ломает работу.** Проверяется: JSON-объект, `mode` из двух значений, оба
раздела со строками `url` и `model`, у активного режима `url` начинается с `http://` или
`https://`, а `model` не пуст. Если файл не читается, не разбирается или не проходит проверку,
запрос идёт по последней корректной конфигурации (она хранится в общей памяти nginx и переживает
reload), а в лог пишется `llm-proxy: /etc/llm-proxy/config.json некорректен (...)`. Если корректной
конфигурации не было с самого запуска контейнера, `/v1/chat/completions` отвечает 503;
`/healthz` при этом остаётся 200 (прокси жив, ему нечего делать).

**Адрес Ollama зависит от режима стека.** Умолчание `https://ollama:8443/v1` — для стека с
`docker-compose.mtls.yml` (Ollama за mTLS-прокси). Без оверлея Ollama слушает
`http://ollama:11434/v1`, это значение и нужно записать в `ollama.url`. Модель Ollama по умолчанию
пуста: режим `ollama` заработает, когда её укажут (и она скачана `ollama-init`).

## Ключ роутера

`ROUTER_KEY` задаётся в `main/.env` и попадает только в окружение контейнера `llm-proxy`
(`env ROUTER_KEY;` в `nginx.conf` делает его видимым для njs). В `config.json`, файлы конфигурации
nginx, логи и ответы он не попадает: шаблон отрисовывается `envsubst` только по переменным
`LLM_PROXY_*`, лог не содержит заголовков и тел. Если ключ пуст, режим `router` отвечает 503 и пишет
в лог `ROUTER_KEY не задан`.

В режиме `router` любой присланный клиентом `Authorization` заменяется на `Bearer $ROUTER_KEY`, в
режиме `ollama` заголовок не отправляется вовсе. Сертификат роутера проверяется по системным
корневым сертификатам образа, чтобы ключ не ушёл подменённому серверу.

Кто может писать `config.json`, тот может направить запросы с ключом на любой адрес (`router.url`).
Поэтому доступ к тому на запись — только у прокси и, когда появится переключение настроек, у
админки `db-svc` за правами администратора; страница настроек подключает том только на чтение.

## Что принимает

| Запрос | Ответ |
| :-- | :-- |
| `POST /v1/chat/completions` | тело уходит на `<url>/chat/completions` активного режима с `model` режима; ответ, в том числе SSE (`"stream": true`), идёт потоком |
| `GET /healthz` | 200 на обычном HTTP-входе; на mTLS-входе 8443 — 403 (политика по CN пускает только `POST /v1/chat/completions`), живость проверяется изнутри контейнера по `127.0.0.1:8080` |
| всё остальное (`/v1/models`, `/v1/embeddings`, другие методы) | 403 |

Свои ответы прокси: 400 — тело не JSON-объект; 503 — нет корректной конфигурации или нет ключа
для режима `router`; 502 — upstream недоступен или его имя не разрешается (сам nginx при этом не
падает: адрес приходит из файла и разрешается на каждом запросе через DNS docker).

## Как устроено

- `nginx.conf` — main-контекст: загрузка njs, `env ROUTER_KEY;`.
- `default.conf.template` — уровень http и обычный HTTP-сервер. Отрисовывается штатным `envsubst`
  образа в `/etc/nginx/conf.d/default.conf`; подставляется только `LLM_PROXY_LISTEN`.
- `locations.conf` — маршруты, общие для обычного и mTLS-входа.
- `llm.js` — `loadConfig` (чтение и проверка файла, последняя корректная версия),
  `rewriteBody` (подмена `model`, остальные поля без изменений), `route`.
- `entrypoint.sh` — создаёт `config.json` по умолчанию и запускает штатную точку входа образа.

Тело запроса читает njs (`js_content`), подменяет `model`, кладёт готовое тело и адрес upstream в
переменные и делает `internalRedirect` в `@router` или `@ollama`; дальше работает обычный
`proxy_pass $llm_url` с `proxy_set_body $llm_body` и `proxy_buffering off`. Так njs только готовит
запрос, а передачу ответа делает nginx — SSE идёт порциями. Подзапросы njs (`r.subrequest`,
`ngx.fetch`) не годятся: они собирают ответ целиком. `js_set` тоже: он не видит тело запроса, а
файл в нём пришлось бы читать второй раз, и модель с адресом могли бы взяться из разных версий
файла. Поэтому файл читается один раз в `route`, а `js_set` вычисляет только заголовок
`Authorization` для `@router`.

## mTLS

С `docker-compose.mtls.yml` прокси принимает запросы на `https://llm-proxy:8443` только с
клиентским сертификатом нашего CA и только от CN `graph-rag-svc` на `POST /v1/chat/completions`
(`infra/mtls/llm-proxy.conf`). Обычный вход переводится на `127.0.0.1:8080` и нужен только
проверке живости изнутри контейнера. В режиме `ollama` прокси сам ходит в Ollama по mTLS со своим
сертификатом (CN `llm-proxy`, `ollama_client_tls.conf`); `infra/mtls/ollama.conf` пускает его только
на `/v1/chat/completions`. Сертификат выпускается `scripts/pki/enroll.sh llm-proxy`, обновляет его
`llm-proxy-certs` с `SIGHUP` nginx.

**Почему без сайдкара.** У остальных сервисов mTLS снимает nginx-сайдкар в их сетевом пространстве,
потому что приложение (uvicorn) само этого не умеет. llm-proxy и есть nginx: второй nginx перед ним
ничего бы не добавил, кроме лишнего звена и ограничения Docker с общим сетевым пространством (см.
`infra/pki/README.md`). Поэтому сервер на 8443 с `ssl_verify_client on` и политикой по CN
подключается прямо в его конфигурацию, а маршруты у обоих входов общие (`locations.conf`).

`graph-rag-svc` ходит на `http://llm-proxy:8080/v1` в базовом стеке и на `https://llm-proxy:8443/v1`
с mTLS-оверлеем (`LLM_BASE_URL` в `docker-compose.yml` / `docker-compose.mtls.yml`) и стартует только
после healthy `llm-proxy`. Сквозная проверка `graph-rag-svc` через настоящий прокси —
`tests/test_notebook_pipeline_flow.py` в корне `main`, только по HTTP (порт 8080); mTLS-путь (8443)
проверяется `llm_proxy_policy.sh` и не покрыт сквозным тестом с настоящим образом `graph-rag-svc`.

## Логи

Строка доступа: адрес, метод, путь, статус, размер, время, режим, модель, статус upstream и DN
клиентского сертификата. Заголовков (`Authorization`) и тел нет. Ошибки конфигурации и отсутствие
ключа — в журнале ошибок nginx; оба потока видны в `docker logs llm-proxy`.

## Проверка

На одноразовых контейнерах, настоящие роутер и Ollama не используются:

- `bash infra/llm-proxy/tests/proxy_e2e.sh` — заглушка upstream (`tests/upstream_stub.py`) под
  именами роутера и Ollama: подмена модели и ключа, сохранность остального тела, горячая смена
  режима, модели и адреса, битый файл и неизвестный `mode`, 503 без корректного файла и без ключа,
  поток SSE в обоих режимах, HTTPS к роутеру (одноразовый CA подкладывается на место системного
  набора `/etc/ssl/certs/ca-certificates.crt`: доверенный сертификат проходит с верным SNI, чужой CA
  и чужое имя дают 502, и запрос с ключом до такого сервера не доходит), 403 на чужие пути, 502 на
  неразрешимый адрес, отсутствие ключа и тел в логах.
- `bash infra/mtls/tests/llm_proxy_policy.sh` — одноразовый CA, цепочка
  `graph-rag-svc → llm-proxy:8443 → ollama-mtls → заглушка`, политика по CN, закрытый порт 8080,
  `SIGHUP`.
- `bash infra/mtls/tests/ollama_policy.sh` — политика Ollama, в том числе CN `llm-proxy`.

Поток проверяется в двух разметках. Chunked-ответ (так отвечают роутеры по HTTP/1.1) nginx 1.27
отдаёт порциями даже при `proxy_buffering on`, а ответ без длины, до закрытия соединения, при
включённой буферизации придерживает до конца — на нём тест и ловит `proxy_buffering on`, в том
числе выставленный только в `@router` или только в `@ollama`.
