# Внутренний центр сертификации (step-ca)

Даёт сервисам короткоживущие сертификаты для взаимной TLS-аутентификации (mTLS): сервис
доказывает, кто он, не секретом из `.env`, а сертификатом с именем `chat-svc`, `postgres` и т. п.,
выпущенным нашим центром сертификации. Сертификат живёт сутки и обновляется сам; украденный
ключ почти сразу теряет силу, а общих паролей, которые надо менять во всех сервисах разом,
нет.

Это шаг до переезда в Kubernetes: там сертификаты сервисам выдаст Linkerd, а здесь тот же
принцип работает на compose. Корень этого CA задуман как будущий trust anchor для Linkerd (см.
«Переезд в Kubernetes»).

## Устройство

```
Pochemuchnik Root CA          10 лет, ключ ТОЛЬКО в pki/root/ и офлайн-копии
        │ подписывает
Pochemuchnik Intermediate CA  5 лет, pathlen:0 — ключ в томе step_ca_data, им работает step-ca
        │ подписывает
сертификаты сервисов          24 часа (PKI_CERT_TTL); CN и SAN = имя сервиса; серверные и клиентские
```

- **Корень не в стеке.** Его ключ нужен раз в несколько лет, чтобы выпустить новый
  промежуточный сертификат. Скомпрометированный CA (контейнер, том) позволяет подделывать
  сервисы, но не создавать новые центры; корень меняется без переделки каждого сервиса,
  потому что сервисы доверяют корню, а не промежуточному.
- **Промежуточный сертификат с `pathlen:0`** не может выпускать подчинённые CA, только
  конечные сертификаты.
- **Идентичность = имя.** Решение «этому сервису можно вызывать то-то» принимается по имени в
  сертификате. Кто какое имя может получить, определяется токеном при выдаче.

## Запуск

```bash
scripts/pki/init.sh                              # один раз: корень, промежуточный, конфигурация
docker compose --profile pki up -d step-ca       # CA; наружу порт не публикуется
scripts/pki/enroll.sh chat-svc                   # первый сертификат сервиса (том pki_certs_chat-svc)
```

`init.sh` печатает отпечаток корня и просит увезти `pki/root/` (ключ корня и пароль к нему) с
машины. Каталог `pki/` в `.gitignore`: публичный `pki/root_ca.crt` раздаётся сервисам, всё
остальное в репозиторий попадать не должно.

`enroll.sh <имя> [--san ещё.имя] [--uid N --gid N] [--volume ТОМ]` выпускает сертификат и кладёт
в том `tls.crt` (лист и промежуточный), `tls.key` (0600) и `root_ca.crt`. `--uid/--gid` — кому
принадлежат файлы: для postgres это его пользователь, иначе он откажется читать ключ.

### Как сервис получает сертификат

Первый сертификат выдаётся по **одноразовому токену**: JWT на 5 минут, подписанный ключом
провизионера и содержащий допустимые имена. Эти свойства проверяются самопроверкой:

- токен для `alpha` не даёт сертификат `beta`;
- использованный токен повторно не принимается, подделанный тоже;
- токен минтит `enroll.sh`, то есть тот, кто может выполнять `docker exec` в контейнер CA.

Это честное ограничение compose: аттестации сервиса, как в SPIRE или Kubernetes
(ServiceAccount-токен), здесь нет, поэтому доверие к «этому контейнеру можно выдать имя
`chat-svc`» держится на операторе. В Kubernetes эту роль возьмёт платформа.

### Обновление

После первой выдачи токены не нужны: рядом с сервисом работает контейнер, который обновляет
сертификат по самому сертификату (mTLS к CA), примерно за треть срока до истечения.
Заготовка (подставьте имя; в ней два контейнера делят один том):

```yaml
  chat-svc-certs:
    image: smallstep/step-ca:0.30.2
    profiles: ["pki"]
    user: "0"                       # сохраняет владельца файлов, заданного при выдаче
    entrypoint: ["/bin/sh", "/renewer.sh"]
    environment:
      CA_URL: https://step-ca:9000
      # RENEW_EXEC: "kill -HUP 1"   # что сделать после обновления, если сервису нужен сигнал
    volumes:
      - pki_certs_chat-svc:/certs
      - ./infra/pki/renewer.sh:/renewer.sh:ro
    networks: [pki-net]

volumes:
  pki_certs_chat-svc:
    external: true                  # создан enroll.sh
```

Сервис монтирует тот же том только на чтение. Если стек простоял дольше срока жизни,
сертификат истёк и обновить его уже нельзя: выполните `enroll.sh` заново.

## Срок жизни

По умолчанию 24 часа, задаётся `PKI_CERT_TTL` в корневом `.env`:

```bash
# .env: PKI_CERT_TTL=168h
docker compose --profile pki up -d step-ca
```

Меняется только срок **новых** сертификатов; выданные живут до своего конца. Минимум 5 минут,
значение вида `24h`, `168h`, `90m`; неверное останавливает запуск CA с понятной ошибкой.
Для dev-стека, который выключают на выходные, удобна неделя: при суточном сроке в понедельник
сертификаты придётся выдавать заново.

## Отзыв

Отдельного списка отзыва нет: опора на короткий срок. Скомпрометированный ключ сервиса
перестаёт работать через сутки (максимум `PKI_CERT_TTL`), если не дать ему обновиться. Чтобы
не дать, достаточно остановить обновляющий контейнер и не выдавать новый токен. При
компрометации самого CA: `scripts/pki/init.sh --force` создаёт всё заново (все сертификаты
станут недействительны, сервисам нужна повторная выдача). Если скомпрометирован только том
CA, а корень цел, достаточно выпустить новый промежуточный сертификат корневым ключом из офлайна.

## Проверка

```bash
infra/pki/tests/selftest.sh
```

Поднимает одноразовый CA со своей сетью и томами (настоящий не затрагивается, префикс
`pkiselftest`) и проверяет: цепочку до корня, имена и назначение сертификата, срок жизни,
привязку и одноразовость токена, обновление (владелец и права ключа сохраняются), что
самоподписанный «двойник» не может обновиться, mTLS (принят клиент с сертификатом нашего CA,
отвергнуты клиент без сертификата и клиент с чужим), смену срока через `PKI_CERT_TTL`,
отсутствие корневого ключа в томе CA. `SELFTEST_DEBUG=1` показывает вывод рукопожатия.
Запускается около двух минут, образ `smallstep/step-ca` скачивается один раз.

Отдельная проверка Postgres и db-svc по сертификатам: `infra/pki/tests/postgres_cert_auth.sh`.

## mTLS между сервисами

`docker-compose.mtls.yml` закрывает сертификатами два сервиса, к которым ходят только другие
сервисы: graph-rag-svc и embedding-svc.

```
chat-svc ──► graph-rag-svc   /generate, /cancel
db-svc   ──► graph-rag-svc   /internal/graph/*
graph-rag-svc, ingest-worker ──► embedding-svc   /embed, /ping
```

**Как устроено.** Рядом с получателем работает прокси (nginx) **в том же сетевом пространстве**
(`network_mode: service:...`). Приложение переводится на `127.0.0.1`, поэтому из другого
контейнера до него не достучаться: открыт только порт 8443 прокси, который требует клиентский
сертификат нашего CA. Что вызывающему можно, решает его CN: правила лежат в
`infra/mtls/graph-rag-svc.conf` и `infra/mtls/embedding-svc.conf` (путь нормализуется, поэтому
обход через `/generate/../internal/graph/` не работает). Приложению прокси сообщает проверенное
имя вызывающего в `X-Caller-Identity`, присланное клиентом значение отбрасывается. Статические
токены `X-Service-Token` остаются вторым слоем.

**Вызывающие** используют `app/mtls.py` (одинаков в chat-svc, db-svc, graph-rag-svc,
ingest-worker): контекст TLS с их сертификатом собирается при создании каждого HTTP-клиента, а
клиенты создаются на каждый вызов, так что суточный сертификат подхватывается без
перезапуска. Без `SERVICE_MTLS_CERT` всё работает как раньше, по открытому HTTP.

**Включение**

```bash
for s in chat-svc db-svc graph-rag-svc embedding-svc ingest-worker; do scripts/pki/enroll.sh "$s"; done
# в .env: COMPOSE_FILE=docker-compose.yml:docker-compose.pki.yml:docker-compose.mtls.yml
docker compose --profile pki up -d --no-deps graph-rag-svc graph-rag-svc-mtls graph-rag-svc-certs \
    embedding-svc embedding-svc-mtls embedding-svc-certs chat-svc chat-svc-certs \
    db-svc db-svc-certs ingest-worker ingest-worker-certs
```

**Ограничение Docker.** Прокси живёт в сетевом пространстве получателя. Если получатель
перезапускается (`docker restart`, падение и подъём по `restart: unless-stopped`) или
пересоздаётся, прокси остаётся в его прежнем пространстве и перестаёт принимать соединения, пока
его не перезапустить. Compose сам перезапускает прокси при пересоздании получателя через
`docker compose up` (в файле для этого `depends_on`), но не при падениях и подъёмах по
политике `restart`. Для получателя, который стабильно работает, это не проблема; получатель в
цикле перезапусков (как graph-rag-svc, пока недоступен embedding-svc) нужно чинить раньше, чем
включать mTLS. В Kubernetes и Linkerd этой проблемы нет: прокси и приложение — один под.

**Состояние на этом стенде.** `COMPOSE_FILE` в `.env` включает `docker-compose.mtls.yml`, chat-svc
и db-svc уже работают с клиентскими сертификатами и ходят на `https://graph-rag-svc:8443`.
embedding-svc, ollama, graph-rag-svc и ingest-worker по договорённости не запущены (embedding-svc
держит GPU, без него graph-rag-svc и ingest-worker не стартуют), поэтому проверка пути
«вопрос → ответ» через прокси возможна только на одноразовых контейнерах
(`infra/mtls/tests/mtls_e2e.sh`). Сертификаты graph-rag-svc, embedding-svc и ingest-worker выпущены
на сутки и обновляются только пока работают их обновляющие контейнеры: перед запуском этих
сервисов выпустите их заново (`scripts/pki/enroll.sh <имя>`, он перезаписывает том), затем
`docker compose --profile pki up -d --no-deps` для самих сервисов, их прокси `*-mtls` и
`*-certs`. Прокси запускается после получателя, а при перезапуске получателя его нужно
перезапустить тоже.

**Проверка**: `infra/mtls/tests/mtls_e2e.sh` — политика по таблице «кто что может», отказ без
сертификата и с самоподписанным «двойником», невозможность обойти прокси, настоящий клиентский код
сервисов и перечитывание сертификата прокси после обновления.

**Не закрыто этим шагом.** Вызовы chat-svc → auth-svc (`/internal/users/...`) и
graph-rag-svc → chat-svc (WebSocket `/ws/internal/llm`) идут по-прежнему на токенах: оба
получателя обслуживают ещё и nginx, поэтому для них нужен клиентский сертификат у шлюза.

## Переезд в Kubernetes

Корень и порядок доверия рассчитаны на Linkerd: его идентичность сервисов строится из trust
anchor и issuer-сертификата, а Linkerd проверяет, что issuer подписан anchor. Предполагается
взять наш корень как anchor, а промежуточный сертификат (`CA:TRUE`) как issuer (его выпускает
cert-manager или вручную тем же корнем), тогда уже выданные сертификаты и новые идентичности
Linkerd будут в одной цепочке доверия. Это нужно проверить на месте до переезда: требования
Linkerd к issuer (срок, `pathlen`, ключи) меняются между версиями.

## Что здесь не сделано

- **Использование сертификатов сервисами.** Postgres и все сервисы, ходящие в него, умеют
  работать по сертификатам (`infra/db/README.md`, `docker-compose.pki.yml`), а graph-rag-svc и
  embedding-svc принимают вызовы только по mTLS (см. выше). Остальные HTTP-связи, в первую
  очередь те, где получатель обслуживает и nginx (auth-svc, chat-svc), пока на токенах.
- **Высокая доступность CA.** Один экземпляр. Если он упал, существующие сертификаты
  работают до истечения, обновиться нельзя; при суточном сроке запас — несколько часов.
- **Резервная копия.** Том `step_ca_data` (ключ промежуточного CA, пароль, база выданных
  сертификатов) и `pki/root/` стоит копировать.
