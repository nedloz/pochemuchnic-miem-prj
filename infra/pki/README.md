# Внутренний центр сертификации (step-ca)

Даёт сервисам короткоживущие сертификаты для взаимной TLS-аутентификации (mTLS): сервис
доказывает, кто он, не секретом из `.env`, а сертификатом с именем `chat-svc`, `postgres` и т. п.,
выпущенным нашим центром сертификации. Сертификат живёт сутки и обновляется сам; украденный
ключ почти сразу теряет силу, а общих паролей, которые надо менять во всех сервисах разом,
нет.

Это шаг до переезда в Kubernetes: там сертификаты сервисам выдаст Linkerd, а здесь тот же
принцип работает на compose. Корень этого CA задуман как будущий trust anchor для Linkerd (см.
«Переезд в Kubernetes»).

## Устройство

```
Pochemuchnik Root CA          10 лет, ключ ТОЛЬКО в pki/root/ и офлайн-копии
        │ подписывает
Pochemuchnik Intermediate CA  5 лет, pathlen:0 — ключ в томе step_ca_data, им работает step-ca
        │ подписывает
сертификаты сервисов          24 часа (PKI_CERT_TTL); CN и SAN = имя сервиса; серверные и клиентские
```

- **Корень не в стеке.** Его ключ нужен раз в несколько лет, чтобы выпустить новый
  промежуточный сертификат. Скомпрометированный CA (контейнер, том) позволяет подделывать
  сервисы, но не создавать новые центры; корень меняется без переделки каждого сервиса,
  потому что сервисы доверяют корню, а не промежуточному.
- **Промежуточный сертификат с `pathlen:0`** не может выпускать подчинённые CA, только
  конечные сертификаты.
- **Идентичность = имя.** Решение «этому сервису можно вызывать то-то» принимается по имени в
  сертификате. Кто какое имя может получить, определяется токеном при выдаче.

## Запуск

```bash
scripts/pki/init.sh                              # один раз: корень, промежуточный, конфигурация
docker compose --profile pki up -d step-ca       # CA; наружу порт не публикуется
scripts/pki/enroll.sh chat-svc                   # первый сертификат сервиса (том pki_certs_chat-svc)
```

`init.sh` печатает отпечаток корня и просит увезти `pki/root/` (ключ корня и пароль к нему) с
машины. Каталог `pki/` в `.gitignore`: публичный `pki/root_ca.crt` раздаётся сервисам, всё
остальное в репозиторий попадать не должно.

`enroll.sh <имя> [--san ещё.имя] [--uid N --gid N] [--volume ТОМ]` выпускает сертификат и кладёт
в том `tls.crt` (лист и промежуточный), `tls.key` (0600) и `root_ca.crt`. `--uid/--gid` — кому
принадлежат файлы: для postgres это его пользователь, иначе он откажется читать ключ.

### Как сервис получает сертификат

Первый сертификат выдаётся по **одноразовому токену**: JWT на 5 минут, подписанный ключом
провизионера и содержащий допустимые имена. Эти свойства проверяются самопроверкой:

- токен для `alpha` не даёт сертификат `beta`;
- использованный токен повторно не принимается, подделанный тоже;
- токен минтит `enroll.sh`, то есть тот, кто может выполнять `docker exec` в контейнер CA.

Это честное ограничение compose: аттестации сервиса, как в SPIRE или Kubernetes
(ServiceAccount-токен), здесь нет, поэтому доверие к «этому контейнеру можно выдать имя
`chat-svc`» держится на операторе. В Kubernetes эту роль возьмёт платформа.

### Обновление

После первой выдачи токены не нужны: рядом с сервисом работает контейнер, который обновляет
сертификат по самому сертификату (mTLS к CA), примерно за треть срока до истечения.
Заготовка (подставьте имя; в ней два контейнера делят один том):

```yaml
  chat-svc-certs:
    image: smallstep/step-ca:0.30.2
    profiles: ["pki"]
    user: "0"                       # сохраняет владельца файлов, заданного при выдаче
    entrypoint: ["/bin/sh", "/renewer.sh"]
    environment:
      CA_URL: https://step-ca:9000
      # RENEW_EXEC: "kill -HUP 1"   # что сделать после обновления, если сервису нужен сигнал
    volumes:
      - pki_certs_chat-svc:/certs
      - ./infra/pki/renewer.sh:/renewer.sh:ro
    networks: [pki-net]

volumes:
  pki_certs_chat-svc:
    external: true                  # создан enroll.sh
```

Сервис монтирует тот же том только на чтение. Если стек простоял дольше срока жизни,
сертификат истёк и обновить его уже нельзя: выполните `enroll.sh` заново.

## Методичка: запуск PKI и выпуск сертификатов

**Что автоматически, а что нет.** Автоматически только *обновление*: пока работает контейнер
`<сервис>-certs`, сертификат продлевается сам (примерно за треть срока до конца). *Первый*
сертификат выдаётся вручную `scripts/pki/enroll.sh`, а если контейнер-обновлялка остановился и
сертификат успел истечь (по умолчанию живёт 24 часа), выпуск нужно повторить: обновить истёкший
сертификат нельзя. Ни `docker compose up`, ни перезагрузка машины сертификаты не выпускают.

### 1. С нуля (один раз на машину)

```bash
scripts/pki/init.sh                               # корень, промежуточный сертификат, конфиг CA
docker compose --profile pki up -d step-ca        # CA; ждём healthy: docker ps | grep step-ca
```

`init.sh` печатает отпечаток корня; каталог `pki/root/` (ключ корня и пароль) увезите с машины.
Повторный запуск без `--force` откажется работать; `--force` обнуляет CA и делает недействительными
все выданные сертификаты.

### 2. Выпуск сертификатов

Имя в команде = идентичность = CN: по нему `infra/mtls/*.conf` решают, что вызывающему можно.

```bash
# Сервисы за mTLS (docker-compose.mtls.yml). Первые пять нужны для входа пользователя;
# graph-rag-svc, embedding-svc, ingest-worker, ollama нужны, только если эти сервисы запускаются
for s in nginx auth-svc chat-svc library-svc db-svc redis minio; do scripts/pki/enroll.sh "$s"; done
for s in graph-rag-svc embedding-svc ingest-worker; do scripts/pki/enroll.sh "$s"; done   # по необходимости

# Postgres: сервер (999 = пользователь postgres) и клиентские сертификаты, CN = имя роли в БД
scripts/pki/enroll.sh postgres --uid 999 --gid 999
for role in auth_user chat_user library_user ingest_user graph_user dbsvc_user; do scripts/pki/enroll.sh "$role"; done

# Наблюдаемость (если включена)
scripts/pki/enroll.sh prometheus --uid 65534 --gid 65534
scripts/pki/enroll.sh redis-exporter --uid 59000 --gid 59000
```

Имена ролей БД берите из `.env` (`AUTH_DB_USER` и т. д.). `enroll.sh` перезаписывает том, поэтому
его можно запускать повторно. Нужен запущенный `step-ca`.

### 3. Запуск обновляющих контейнеров и сервисов

В `.env` должно быть `COMPOSE_FILE=docker-compose.yml:docker-compose.pki.yml:docker-compose.mtls.yml`.
Профиль `pki` включает `*-certs`; **если в `.env` стоит `COMPOSE_PROFILES=llm`, перекройте его**, иначе
поднимется ollama:

```bash
export COMPOSE_PROFILES=pki
docker compose up -d --no-deps \
    auth-svc auth-svc-mtls auth-svc-certs  library-svc library-svc-mtls library-svc-certs \
    chat-svc chat-svc-mtls chat-svc-certs  db-svc db-svc-mtls db-svc-certs \
    minio minio-mtls minio-certs  redis redis-mtls redis-certs
docker compose up -d --no-deps nginx nginx-certs      # шлюз последним: имена апстримов он разрешает при старте
```

### 4. Проверка

```bash
docker ps --format '{{.Names}}\t{{.Status}}' | grep -E 'certs|mtls'     # *-certs должны быть Up, не Exited
for s in nginx auth-svc chat-svc library-svc db-svc redis minio; do
  echo -n "$s: "; docker run --rm -v pki_certs_$s:/c:ro --entrypoint sh alpine/openssl \
      -c 'openssl x509 -in /c/tls.crt -noout -enddate'; done                # дата должна быть в будущем
```

Быстрая проверка пути пользователя: `POST /api/auth/login` через nginx вернёт токен.

### 5. Если что-то сломалось

| Симптом | Причина | Что делать |
| ------- | ------- | ---------- |
| nginx отвечает 502, в его логе `upstream SSL certificate verify error: (10:certificate has expired)` | сертификат сервиса или шлюза истёк: `*-certs` был остановлен (перезагрузка Docker, `kill`, выключенная машина) | `enroll.sh <имя>` для истёкших, затем `restart` их `*-mtls`, запустить `*-certs`, `restart nginx` |
| `Exited (137)` или `Exited (128)` у `*-certs` | контейнер убит | проверить срок сертификата (п. 4); если ещё валиден, достаточно `up -d --force-recreate <сервис>-certs`, иначе выпустить заново |
| `failed to join PID namespace: No such container` | `*-certs` делит PID-пространство с `*-mtls`/nginx, а те пересозданы | `docker compose up -d --no-deps --force-recreate <сервис>-certs` |
| после пересоздания сервиса его порт 8443 не отвечает | прокси остался в старом сетевом пространстве | `docker compose up -d` сам перезапускает прокси; при `docker restart` вручную: `docker restart <сервис>-mtls` |
| `enroll.sh`: «контейнер step-ca не запущен» | CA остановлен | `docker compose --profile pki up -d step-ca` |
| сервис отвечает 403 | CN не разрешён политикой | правило в `infra/mtls/<получатель>.conf` (кто что может) |

Чтобы стенд, который выключают на выходные, не требовал повторной выдачи в понедельник, поставьте
`PKI_CERT_TTL=168h` в `.env` (см. «Срок жизни»); сроки уже выданных сертификатов это не меняет.

## Срок жизни

По умолчанию 24 часа, задаётся `PKI_CERT_TTL` в корневом `.env`:

```bash
# .env: PKI_CERT_TTL=168h
docker compose --profile pki up -d step-ca
```

Меняется только срок **новых** сертификатов; выданные живут до своего конца. Минимум 5 минут,
значение вида `24h`, `168h`, `90m`; неверное останавливает запуск CA с понятной ошибкой.
Для dev-стека, который выключают на выходные, удобна неделя: при суточном сроке в понедельник
сертификаты придётся выдавать заново.

## Отзыв

Отдельного списка отзыва нет: опора на короткий срок. Скомпрометированный ключ сервиса
перестаёт работать через сутки (максимум `PKI_CERT_TTL`), если не дать ему обновиться. Чтобы
не дать, достаточно остановить обновляющий контейнер и не выдавать новый токен. При
компрометации самого CA: `scripts/pki/init.sh --force` создаёт всё заново (все сертификаты
станут недействительны, сервисам нужна повторная выдача). Если скомпрометирован только том
CA, а корень цел, достаточно выпустить новый промежуточный сертификат корневым ключом из офлайна.

## Проверка

```bash
infra/pki/tests/selftest.sh
```

Поднимает одноразовый CA со своей сетью и томами (настоящий не затрагивается, префикс
`pkiselftest`) и проверяет: цепочку до корня, имена и назначение сертификата, срок жизни,
привязку и одноразовость токена, обновление (владелец и права ключа сохраняются), что
самоподписанный «двойник» не может обновиться, mTLS (принят клиент с сертификатом нашего CA,
отвергнуты клиент без сертификата и клиент с чужим), смену срока через `PKI_CERT_TTL`,
отсутствие корневого ключа в томе CA. `SELFTEST_DEBUG=1` показывает вывод рукопожатия.
Запускается около двух минут, образ `smallstep/step-ca` скачивается один раз.

Отдельная проверка Postgres и db-svc по сертификатам: `infra/pki/tests/postgres_cert_auth.sh`.

## mTLS между шлюзом и сервисами и между сервисами

`docker-compose.mtls.yml` закрывает сертификатами все HTTP-связи в стеке: до любого сервиса можно
достучаться только с клиентским сертификатом нашего CA, а что именно вызывающему можно, решает
его CN.

```
nginx    ──► auth-svc      /auth/*, /users/me           (но не /internal/*)
nginx    ──► chat-svc      /ws/chat (WebSocket)
nginx    ──► library-svc   /library/*, /api/documents/*
nginx    ──► db-svc        админ-панель
chat-svc ──► auth-svc      /internal/users/{id}/profile
chat-svc ──► graph-rag-svc /generate, /cancel
db-svc   ──► graph-rag-svc /internal/graph/*
graph-rag-svc ──► chat-svc /ws/internal/llm (WebSocket)
graph-rag-svc, ingest-worker ──► embedding-svc   /embed, /ping
```

**Как устроено.** Рядом с получателем работает прокси (nginx) **в том же сетевом пространстве**
(`network_mode: service:...`). Приложение переводится на `127.0.0.1`, поэтому из другого
контейнера до него не достучаться: открыт только порт 8443 прокси, который требует клиентский
сертификат нашего CA. Правила «кто что может» лежат в `infra/mtls/<сервис>.conf` (путь
нормализуется, поэтому обход через `/generate/../internal/graph/` не работает). Приложению прокси
сообщает проверенное имя вызывающего в `X-Caller-Identity`, присланное клиентом значение
отбрасывается. Приложение верит этому заголовку только от loopback (тот же сетевой namespace, где стоит прокси), и сервис, до которого можно достучаться мимо прокси, внутренние маршруты не обслуживает. Статических токенов нет: режим `INTERNAL_AUTH_MODE=mtls` по умолчанию, `insecure` нужен только для отладки без PKI и пишет предупреждение при старте.

**Шлюз.** nginx тоже имеет сертификат (идентичность `nginx`). Его конфиг один на оба режима:
`nginx.conf` — шаблон, схему и порт апстримов (`http`/`8000` или `https`/`8443`) подставляет
`envsubst` образа из переменных `UPSTREAM_SCHEME` и `UPSTREAM_PORT`, а `proxy_ssl_*` подключаются
файлом `infra/nginx/backend_tls.conf` только в режиме mTLS. Шлюзу разрешены публичные пути
сервисов и запрещён `/internal/*`: даже скомпрометированный шлюз до внутренних маршрутов не
доберётся. После обновления сертификата шлюз получает `SIGHUP` (контейнер `nginx-certs`).

**Вызывающие** используют `app/mtls.py` (одинаков в chat-svc, db-svc, graph-rag-svc,
ingest-worker): контекст TLS с их сертификатом собирается при создании каждого HTTP-клиента или
WebSocket-подключения, так что суточный сертификат подхватывается без перезапуска. Без
`SERVICE_MTLS_CERT` всё работает как раньше, по открытому HTTP.

**Включение**

```bash
for s in nginx auth-svc chat-svc library-svc db-svc graph-rag-svc embedding-svc ingest-worker; do
    scripts/pki/enroll.sh "$s"; done
# в .env: COMPOSE_FILE=docker-compose.yml:docker-compose.pki.yml:docker-compose.mtls.yml
docker compose --profile pki up -d --no-deps auth-svc auth-svc-mtls auth-svc-certs \
    library-svc library-svc-mtls library-svc-certs chat-svc chat-svc-mtls chat-svc-certs \
    db-svc db-svc-mtls db-svc-certs nginx nginx-certs
# graph-rag-svc, embedding-svc и ingest-worker (и их *-mtls, *-certs) — когда будет запущен embedding-svc
```

Сначала получатели и их прокси, потом шлюз: nginx разрешает имена апстримов при старте и без
запущенных сервисов не поднимется.

**Ограничение Docker.** Прокси живёт в сетевом пространстве получателя. Если получатель
перезапускается (`docker restart`, падение и подъём по `restart: unless-stopped`) или
пересоздаётся, прокси остаётся в его прежнем пространстве и перестаёт принимать соединения, пока
его не перезапустить. Compose сам перезапускает прокси при пересоздании получателя через
`docker compose up` (в файле для этого `depends_on`), но не при падениях и подъёмах по
политике `restart`. Для получателя, который стабильно работает, это не проблема; получатель в
цикле перезапусков (как graph-rag-svc, пока недоступен embedding-svc) нужно чинить раньше, чем
включать mTLS. В Kubernetes и Linkerd этой проблемы нет: прокси и приложение — один под.

**Состояние на этом стенде.** embedding-svc, ollama, graph-rag-svc и ingest-worker по договорённости
не запущены (embedding-svc держит GPU, без него graph-rag-svc и ingest-worker не стартуют), поэтому
проверка пути «вопрос → ответ» через прокси возможна только на одноразовых контейнерах. Сертификаты
этих сервисов выпущены на сутки и обновляются только пока работают их обновляющие контейнеры: перед
запуском выпустите их заново (`scripts/pki/enroll.sh <имя>`, он перезаписывает том).

**Проверка**
- `infra/mtls/tests/mtls_e2e.sh` — graph-rag-svc и embedding-svc: политика, отказ без сертификата и
  с самоподписанным «двойником», невозможность обойти прокси, настоящий клиентский код сервисов,
  перечитывание сертификата прокси.
- `infra/mtls/tests/gateway_e2e.sh` — шлюз и пользовательские сервисы: настоящий `nginx.conf` в режиме
  https, прокси перед auth-svc, chat-svc, library-svc, db-svc, политика каждой пары, WebSocket через
  всю цепочку, клиентский код chat-svc и graph-rag-svc, обновление сертификата шлюза.

## Хранилища за mTLS

Redis, MinIO и Ollama закрыты тем же способом, что и сервисы: слушают только `127.0.0.1` в своём
сетевом пространстве, снаружи стоит прокси с проверкой клиентского сертификата нашего CA
(`docker-compose.mtls.yml`, конфиги в `infra/mtls/`). Выпуск: `scripts/pki/enroll.sh redis` (так же
`minio`, `ollama`).

| Хранилище | Прокси | Кто пускается | Дополнительно |
| :-- | :-- | :-- | :-- |
| Redis | nginx `stream`, порт 6380 (`redis.conf`) | auth-svc, chat-svc, redis-exporter (только статистика) | ACL-пользователь на сервис: auth-svc видит `auth:*`, chat-svc `ws:*` и `chat:*`, без `@admin` и `@dangerous`; пользователь `default` выключен |
| MinIO | nginx, порт 8443 (`minio.conf`) | library-svc и ingest-worker читают, db-svc читает и пишет | случайные ключи S3 вместо `minioadmin`; консоль только изнутри |
| Ollama | nginx, порт 8443 (`ollama.conf`) | graph-rag-svc, только `/api/chat` и подобные | управление моделями недоступно; модель тянет `ollama-init` изнутри |

Redis 7 не умеет сопоставлять CN сертификата с ACL-пользователем, поэтому доступ двойной:
сертификат решает, кто вообще может подключиться, пароль ACL-пользователя ограничивает ключи и
команды. Пароли и ACL создаёт `scripts/gen_redis_acl.py` (`secrets/redis/users.acl` хранит только
хэши, пароли лежат в `.env`). Ключи MinIO создаёт `scripts/gen_minio_credentials.py`; права по CN
решает прокси, потому что подпись запросов S3 всё равно требует ключей. Клиентский код:
`app/redis_tls.py` (auth-svc, chat-svc) и `app/s3_tls.py` (library-svc, db-svc, ingest-worker);
контекст TLS собирается заново при каждом соединении, так что суточный сертификат подхватывается
без перезапуска (в redis-py контекст иначе кешируется навсегда, поэтому соединение переопределено).

Тесты на одноразовых контейнерах: `infra/mtls/tests/redis_e2e.sh`, `minio_e2e.sh`,
`ollama_policy.sh` (Ollama проверяется на заглушке, настоящий не запускается).

## Наблюдаемость за mTLS

Prometheus собирает `/metrics` сервисов на `:8443` со своим сертификатом (CN `prometheus`), прокси
пускают его только на `GET /metrics` (и MinIO только на `/minio/v2/metrics/cluster`). redis_exporter
ходит в Redis с сертификатом CN `redis-exporter` и ACL-пользователем `prometheus`. Выпуск:
`scripts/pki/enroll.sh prometheus --uid 65534 --gid 65534` и
`scripts/pki/enroll.sh redis-exporter --uid 59000 --gid 59000`; обновление сертификатов делают
`prometheus-certs` и `redis-exporter-certs` из `docker-compose.observability.mtls.yml`. Проверка
политики: `infra/observability/tests/metrics_policy.sh`. Подробности - `infra/observability/README.md`.

## Переезд в Kubernetes

Корень и порядок доверия рассчитаны на Linkerd: его идентичность сервисов строится из trust
anchor и issuer-сертификата, а Linkerd проверяет, что issuer подписан anchor. Предполагается
взять наш корень как anchor, а промежуточный сертификат (`CA:TRUE`) как issuer (его выпускает
cert-manager или вручную тем же корнем), тогда уже выданные сертификаты и новые идентичности
Linkerd будут в одной цепочке доверия. Это нужно проверить на месте до переезда: требования
Linkerd к issuer (срок, `pathlen`, ключи) меняются между версиями.

## Что здесь не сделано

- **Использование сертификатов сервисами.** Postgres и все сервисы, ходящие в него, умеют работать по
  сертификатам (`infra/db/README.md`, `docker-compose.pki.yml`), а все HTTP-связи в стеке (шлюз →
  сервисы и сервисы между собой) принимаются только по mTLS (`docker-compose.mtls.yml`). Статические
  токены `X-Service-Token` удалены: вызывающего подтверждает только сертификат.
- **Postgres, MinIO, Redis, Ollama** закрыты сертификатами (разделы выше и «Хранилища за mTLS»). Не закрыты только то, чего нет в стеке; консоль MinIO снаружи недоступна, а presigned-ссылки браузеру недоступны вместе с проброшенным портом MinIO.
- **Высокая доступность CA.** Один экземпляр. Если он упал, существующие сертификаты
  работают до истечения, обновиться нельзя; при суточном сроке запас — несколько часов.
- **Резервная копия.** Том `step_ca_data` (ключ промежуточного CA, пароль, база выданных
  сертификатов) и `pki/root/` стоит копировать.
