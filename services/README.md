# Почемучник — карта сервисов и состояние проекта

ИИ-помощник первокурсника НИУ ВШЭ МИЭМ: чат, отвечающий на вопросы об учёбе по
верифицированной базе документов вуза.

Этот файл — точка входа: карта сервисов, текущее состояние работ и сводный список проблем.
Подробности по каждому сервису — в его собственном README.

## Карта сервисов

| Сервис | Роль | Хранилище | README |
| :-- | :-- | :-- | :-- |
| `auth-svc` | Регистрация, JWT/refresh, профиль, роли | Postgres `auth` | [README](auth-svc/README.md) |
| `chat-svc` | Оркестратор диалога: сессии, история, стриминг ответа | Postgres `chat` + Redis | [README](chat-svc/README.md) |
| `graph-rag-svc` | Пайплайн ноутбука: быстрые ответы, гибридный поиск (pgvector + BM25), LLM-реранк, ответ LLM через `llm-proxy`. GraphRAG отключён | читает `library`, пишет `rag` | [README](graph-rag-svc/README.md) |
| `embedding-svc` | Единственный источник эмбеддингов на всю систему (`intfloat/multilingual-e5-base`, 768, `kind` = `query`/`passage`) | stateless | [README](embedding-svc/README.md) |
| `ingest-worker` | Парсинг и чанкинг по ноутбуку → эмбеддинги чанков; эмбеддинги быстрых ответов и ссылок | пишет в Postgres `library` | [README](ingest-worker/README.md) |
| `library-svc` | Каталог документов, дерево тем, выдача файлов | Postgres `library` + MinIO | [README](library-svc/README.md) |
| `db-svc` | Админка: CRUD по всей базе, импорты (в т. ч. Excel быстрых ответов и список ссылок), файлы. Курирование графа отключено | ходит во все схемы | [README](db-svc/README.md) |
| `frontend` | Веб-приложение (React) — лежит в `main/frontend`, а не здесь | — | [README](../main/frontend/README.md) |

Инфраструктура (`main/`): docker-compose, nginx, **`llm-proxy`** (nginx + njs,
`../infra/llm-proxy/README.md`: единственная точка выхода к LLM — внешний роутер или резервная
Ollama по `config.json` на томе, ключ роутера только в его окружении; Ollama — профиль compose
`llm`, по умолчанию выключен), схема БД и миграции, а также **исходники
фронтенда** (`main/frontend`) — nginx собирает их в свой образ и раздаёт статику, поэтому
они лежат в его контексте сборки, а не в `services/`.

**Метрики.** Все HTTP-сервисы отдают `GET /metrics` (Prometheus), `ingest-worker` - на отдельном
порту `METRICS_PORT`. Состав метрик и дашборды - `../infra/observability/README.md`.

**Второй потребитель.** `graph-rag-svc` — общий модуль с соседней командой, которая делает
Telegram-бота без микросервисной архитектуры и использует нашу базу и наш краулер. Контракт
`/generate` двухрежимный именно поэтому. Различия проектов, компромисс и модель владения —
разделы 10–13 в [README graph-rag-svc](graph-rag-svc/README.md).

### Вход в админ-панель

```
Frontend (кнопка видна только роли admin)
   │  POST /api/auth/admin-session   → auth-svc ставит HttpOnly-куку (Path=/admin, 30 мин)
   ▼
Переход на /admin/
   │  nginx: auth_request → /auth/validate-admin (проверка куки в auth-svc)
   │         отказ → 404, к db-svc запрос не уходит
   ▼
db-svc (принимает администратора по подписанному X-User-Context от auth-svc, Bearer-токен в браузер не попадает)
```

Администратор по умолчанию (`admin@edu.hse.ru` / `admin`) создаётся при первой
инициализации базы — иначе войти в панель было бы невозможно, потому что роль `admin`
ставится только в БД. Для локальной разработки это удобно, для публичного стенда пароль
обязательно менять; подробности — в [db-svc/README.md](db-svc/README.md#администратор-по-умолчанию).

### Путь вопроса

```
Frontend ──WS──► chat-svc ──HTTP──► graph-rag-svc
                     ▲                    │ 1. быстрый ответ: embedding-svc (query) + quick_answer_variants
                     │                    │    совпал → готовый текст, LLM не вызывается
                     │                    │ 2. переписывание вопроса (LLM, если есть история)
                     │                    │ 3. pgvector + BM25 по library.chunks → RRF
                     │                    │ 4. LLM-реранк → 1–2 документа с соседними чанками
                     │                    │ 5. ссылки из library.links
                     │                    │ 6. ответ LLM потоком
                     │                    └──► llm-proxy ──► роутер (или Ollama, резерв)
                     └──── /ws/internal/llm ◄── стриминг ответа
```

Бот соседней команды зовёт тот же `/generate` в режиме `sync`.

### Путь документа

```
краулер / db-svc → library.documents + MinIO → ingest-worker → library.chunks (+ chunk_embeddings)
                                                    │
                                     embedding-svc (kind=passage, e5, 768)
                                                    │
db-svc: импорт Excel и all_links.txt → library.quick_answers / quick_answer_variants / links
                                        (без векторов) → ingest-worker досчитывает векторы

graph-rag-svc перестраивает BM25-индекс чанков сам, раз в 60 с по сигнатуре набора чанков.
cli.build_graph → graph.* отключён вместе с GraphRAG.
```

## Текущее состояние

**Октябрь 2026: пайплайн ноутбука.** Ретривал `graph-rag-svc` заменён пайплайном из ноутбука
соседней команды (спецификация `../docs/superpowers/specs/2026-10-27-notebook-pipeline-design.md`):
быстрые ответы без LLM, гибридный поиск, LLM-реранк, агрегация по документам, ссылки. GraphRAG
отключён: код остаётся с пометками `DISABLED`, маршруты курирования в `graph-rag-svc` и `db-svc`
сняты. Все вызовы LLM идут через `llm-proxy`; `ollama` — резерв в профиле `llm`. Эмбеддинги —
`intfloat/multilingual-e5-base` (768), переход — миграция `011` (старые векторы удаляются,
документы уходят на переиндексацию), права воркера — `012`. Новые таблицы: быстрые ответы и
ссылки, их наполняет импорт `db-svc`.

Проверено: модульные тесты сервисов; сборка образов `graph-rag-svc`, `ingest-worker`, `db-svc`;
`docker compose config` для базового стека и mTLS-оверлея; сквозная проверка
`../tests/test_notebook_pipeline_flow.py` на одноразовых контейнерах (настоящие `graph-rag-svc`,
`llm-proxy`, Postgres со всеми миграциями; заглушки `embedding-svc` и upstream LLM). Сквозная
проверка идёт только по HTTP (`llm-proxy:8080`, `INTERNAL_AUTH_MODE=insecure`): mTLS-путь
(`llm-proxy:8443` с клиентским сертификатом `graph-rag-svc`) проверяется отдельно
`../infra/mtls/tests/llm_proxy_policy.sh` и с настоящим образом `graph-rag-svc` не прогонялся;
для mTLS-оверлея проверен только `docker compose config`. С настоящими моделями (e5, роутер) на
живом стеке путь вопроса не прогонялся. Шаги перехода на работающем
стенде — `../deploy.md`, «Миграция на e5».

Для соседней команды изменилось содержимое ответа `/generate` (`route_used` = `quick_answer` |
`hybrid`, `score` = оценка реранка и др.) — список в начале README graph-rag-svc.

Ниже — состояние до октября 2026 (история).

Миграция с классического RAG (`rag-svc` + `llm-svc`) на graph-RAG выполнена в коде, оба
старых сервиса удалены. Реализован разобранный с командой список доработок: единый источник
эмбеддингов с проверкой размерности при запуске, таймауты, отказ отвечать без контекста,
история диалога, человекочитаемые источники, отмена запроса, двухрежимная доставка ответа,
общая аналитика ретривала и инструменты курирования графа.

> **Стек поднят целиком, путь вопроса ещё не прогонялся.**
> Работают все контейнеры, включая `embedding-svc` и `graph-rag-svc`. База инициализируется без
> ошибок, `nginx -t` проходит, фронтенд собирается и отдаётся, вход в админ-панель проверен
> end-to-end на чистой базе. `embedding-svc` отвечает `"device":"cuda"` — модель на GPU;
> `graph-rag-svc` при старте дождался его и подтвердил согласованность размерности (тогда 1024, bge-m3).
>
> Запускать надо на **системном docker-движке**, а не в Docker Desktop: на Linux Desktop держит
> собственную VM, в которую GPU не пробрасывается (`failed to discover GPU vendor from CDI`).
> Нужен `nvidia-container-toolkit` и контекст `default`.
>
> `build_graph` не выполнялся никогда, в схеме `graph` нет ни одной строки, весь graph-путь
> (извлечение сущностей → резолюция → обход → сборка контекста) не исполнялся на реальных
> данных. Под вопросом и сама `library.chunks`: до недавней правки эмбеддингов вставка
> падала, и документы могли остаться в статусе `failed`.

## Порядок ввода в строй

Первый реальный запуск пайплайна ноутбука, снизу вверх. Подробные команды — `../deploy.md`,
«Миграция на e5».

1. **Конфигурация:** `EMBEDDING_DIM=768`, `EMBEDDER_MODEL_NAME=intfloat/multilingual-e5-base`,
   `ROUTER_KEY` в `main/.env`; модель и адрес роутера — в `config.json` тома `llm_proxy_config`.
2. **Миграции** `011_notebook_pipeline.sql` и `012_notebook_grants.sql` (на свежем томе их делает
   `init.sql`) — **только после остановки** `ingest-worker` и `graph-rag-svc`: старый воркер
   забрал бы возвращённые в `pending` документы с векторами 1024 и отправил их в `failed`.
   `graph-rag-svc` и `ingest-worker` не стартуют при расхождении размерности.
3. **Переиндексация:** поднять `embedding-svc` с e5, затем `ingest-worker`; дождаться, пока
   воркер пересчитает все документы (011 вернула их в `pending`), и убедиться, что `failed` —
   ноль. Затем запустить `graph-rag-svc`. Длина чанков относительно окна e5 в 512 токенов на
   корпусе не проверена — проверка в `../deploy.md`.
4. **Быстрые ответы и ссылки:** импорт `HSE_Answers_RU.xlsx` и `all_links.txt` через админку
   `db-svc`; воркер досчитает векторы.
5. **Дёрнуть `/generate` напрямую** в режиме `sync`, минуя chat-svc: быстрый ответ, вопрос по
   документу, вопрос не по теме.
6. **Проверить через фронтенд:** вопрос, уточняющий вопрос (проверка истории), «Остановить».
7. **Прогнать `main/tests/`.** `test_notebook_pipeline_flow.py` — без стека, на одноразовых
   контейнерах; `test_chat_flow_fixed.py` покрывает WS-путь до `question_accepted`.

## Сводка проблем

### Закрыто в последнюю итерацию

| Где | Что было |
| :-- | :-- |
| `nginx` | **Образ не собирался**: Dockerfile копировал `frontend/` из контекста `main/`, а исходники лежали в `services/frontend`. Фронтенд перенесён в `main/frontend`; заодно сборка переведена с `npm install` на `pnpm --frozen-lockfile` (в репозитории только `pnpm-lock.yaml`, и npm его игнорировал), добавлен `.dockerignore` |
| `ingest-worker` | **`Dockerfile` был пустым файлом** — контейнер не собирался вообще, индексация была невозможна в принципе. Восстановлен; заодно убрана бессмысленная публикация порта (HTTP-сервера у воркера нет) |
| `db-svc` | Пустой `DBSVC_ADMIN_TOKEN` молча отключал авторизацию, открывая CRUD по всей базе. Теперь сервис без токена не стартует, а работа без авторизации требует явного `DBSVC_ALLOW_NO_AUTH=true` и пишет предупреждение при каждом старте |
| `postgres`, `minio` | Публиковались на всех интерфейсах. Теперь `ports:` у обоих закомментирован: снаружи виден только `nginx`, остальное — внутри сети compose (проверка: `docker compose config`). Для `psql` с хоста — `docker compose exec postgres psql`. IVHR-5 |
| все сервисы | Межсервисные токены были предсказуемыми заглушками `super-secret-token-for-<имя>` в репозитории (`auth-svc/.env` вообще был закоммичен). Теперь: в `.env.example` стоит `CHANGE_ME`, случайные токены раскладывает `main/scripts/gen_service_tokens.py` (`--rotate` — перевыпуск), принимающие сервисы (`auth-svc`, `chat-svc`, `graph-rag-svc`, `embedding-svc`) не стартуют со слабым токеном (заглушка или короче 24 символов) и сравнивают токены через `hmac.compare_digest`. `auth-svc/.env` убран из git. IVHR-4. **Позже токены удалены совсем**, их заменил mTLS: `gen_service_tokens.py`, `TRUSTED_SERVICE_TOKENS` и `SERVICE_TOKEN` больше не существуют |
| `ingest-worker`, `graph-rag-svc` | `_column_dimension()` была скопирована в оба сервиса, и копии разошлись. Сервисы лежат в разных репозиториях и собираются из своих контекстов, общего Python-модуля у них быть не может, поэтому запрос вынесен в БД: функция `core.vector_column_dimension()` (`init.sql` и `migrations/007_vector_column_dimension.sql`), оба сервиса вызывают её. Миграцию 007 нужно применить до запуска новых версий сервисов. IVHR-14 |
| `frontend` | Обход авторизации (`admin@edu.hse.ru`/`admin`) не был ограничен dev-режимом и попадал в прод-сборку. Обе ветки обёрнуты в `import.meta.env.DEV` — Vite вырезает их при сборке |
| `chat-svc` | Порт публиковался на всех интерфейсах, а сервис доверяет заголовку `X-User-Id` от nginx: прямой доступ к контейнеру позволял подделать заголовок и войти в любую чужую сессию. Публикация убрана |

| `embedding-svc` | Не было лимитов на размер запроса, а сервис — единственный источник эмбеддингов на всю систему. Добавлены лимиты; парно `ingest-worker` научился резать чанки на батчи |
| `embedding-svc` | Ошибка в `TRUSTED_SERVICE_TOKENS` молча превращалась в `403` на все вызовы. Теперь разбор при старте с внятным падением |
| `embedding-svc` | Модель грузилась при импорте модуля: неудачная загрузка роняла процесс, и контейнер уходил в цикл перезапусков. Теперь модель грузится в фоне с повторами; `/health` — liveness, `/ping` — readiness (`503` до загрузки). В compose добавлен healthcheck, потребители ждут `service_healthy` |
| `ingest-worker` | Не было healthcheck, повторов, лимита размера файла, а задачи забирались опросом БД раз в 5 с. Теперь: healthcheck по heartbeat-файлу; повторы с экспоненциальной паузой и возврат брошенных в `processing` документов; `MAX_FILE_SIZE_MB`; доставка задач через `LISTEN/NOTIFY` по триггеру на `library.documents` (миграция `006_ingest_queue.sql`) с опросом как страховкой |
| `db-svc`, `graph-rag-svc`, `embedding-svc` | Порты переведены на петлевой интерфейс (`127.0.0.1:...`): доступ с машины сохранён для отладки, но наружу они не слушают |
| `graph-rag-svc` | Образ безусловно ставил `torch`/`transformers`/`accelerate` — около 5 ГБ колёс `nvidia-*` ради провайдера `LLM_PROVIDER=local`, непригодного для прод-среды. Вынесены в `requirements-local.txt` и ставятся только при сборке с `WITH_LOCAL_LLM=true`; образ похудел с ~6 ГБ до 854 МБ, сборка — с часа до пары минут |
| Схема БД | Роль `admin` ставится только в базе, а до базы добирались через саму панель. `init.sql` теперь заводит администратора по умолчанию; для уже поднятых баз есть `005_seed_admin.sql` |
| `ingest-worker` | Стартовая проверка размерности падала на каждом запуске (7 рестартов подряд): в SQL стояло `attrelid = :rel::regclass`, а SQLAlchemy не распознаёт параметр, за которым сразу идёт `::`, и `:rel` уходил в Postgres буквально. Приведено к `to_regclass(:rel)` — форме, которая уже работала в graph-rag-svc |
| `nginx` | Конфиг раздавал фронтенд как многостраничный сайт: `location = /login { try_files /login.html; }` и ещё семь таких же — наследие прежнего прототипа. Vite собирает один `index.html`, поэтому работал только `/`, а любой маршрут роутера и любая перезагрузка страницы давали 404. Заменено SPA-фолбэком `try_files $uri $uri/ /index.html`; добавлен `location /api/ { return 404; }`, чтобы неизвестный путь под `/api/` не проваливался в фолбэк и не возвращал HTML с кодом 200 |
| `auth-svc` | Чат не подключался вообще: `TRUSTED_SERVICE_TOKENS` у auth-svc содержал для `chat-svc` случайный токен, которого не было больше нигде, и внутренний запрос профиля получал `403`. Остальная сеть сервисов использует общую схему `super-secret-token-for-<имя>` и была согласована; auth-svc приведён к ней |
| `chat-svc` | Чат молчал на любой вопрос: `WsQuestion.request_id` объявлен как `uuid.UUID`, а фронтенд шлёт `req-<время>-<случайное>`. Ошибка валидации выбрасывалась из цикла обработки и закрывала WebSocket целиком — на фронтенде это выглядело как «модель не отвечает». Приведено к `str`, как во всех остальных местах: следующая же строка обработчика делала `str(request.request_id)`, `WsCancel` объявляет строку, graph-rag-svc принимает строку, колонка в `rag.retrieval_runs` — TEXT. Заодно разбор каждого сообщения обёрнут в свой `try`: неверное поле теперь возвращает клиенту ошибку, а не рвёт соединение |
| `db-svc` | Импорт CSV падал с `500`: таблицы журнала `public.dbsvc_jobs` не существовало. Сервис создаёт её при старте, но проверял соединение с базой ровно один раз — стартовав раньше postgres, он получал `Connection refused`, писал ошибку и продолжал работу без таблицы. Обычные запросы при этом работали, поэтому связь с первыми строками лога терялась. Добавлено ожидание `postgres: service_healthy` в compose и цикл повторов при старте; провал создания таблицы теперь логируется уровнем ERROR, а не WARNING |
| `db-svc` | Импорт датасета падал на `order_index ... violates not-null constraint`. Колонки, объявленные в схеме как `NOT NULL DEFAULT`, перечислены в INSERT явно, поэтому пустая ячейка CSV записывала `NULL` и перекрывала значение по умолчанию. Таких колонок шесть (`topics.order_index`, `documents.language/status/priority/scope_json/ingest_status/content_version`) — исправлены все сразу, иначе ошибка повторялась бы по одной на каждый прогон |
| `db-svc` | Импорт датасета в режиме замены **удалял все профили пользователей**. `TRUNCATE ... CASCADE` игнорирует объявленные `ON DELETE SET NULL` и вычищает целиком каждую ссылающуюся таблицу, а на `core.*` ссылается `auth.user_profiles` (и `core.contacts`/`core.places` — на `core.buildings`). Проявилось как пропавшая кнопка админки: `GET /users/me` начал отвечать 404. Заменено на `DELETE`, который правила `ON DELETE` соблюдает |
| `db-svc` | Загрузка HTML клала в MinIO и сырую страницу, и очищенный текст, но в `library.document_files` регистрировала `.html` — переменная `txt_storage_key` дальше не использовалась. `ingest-worker` читает эту таблицу, поэтому в индекс уходила разметка со `<script>` и меню: 126 чанков из 662, а крупные страницы валили `embedding-svc` по размеру запроса. Теперь страница очищается **до** загрузки, в хранилище попадает только `.txt`, а сбой очистки означает, что документ не импортируется вовсе |
| `ingest-worker` | Чанкер не мог разбить кусок, внутри которого нет границ предложений: `_split_sentences` без точек возвращала весь документ одним куском, а предложение длиннее цели уходило в чанк целиком. Отсюда чанки по 19 500 символов. Добавлен `_split_oversized` — жёсткое дробление по словам |
| `ingest-worker` | По логу нельзя было отличить «всё обработано» от «завис»: строка «Ожидаем задачи...» печаталась один раз до цикла, а опустевшую очередь воркер встречал молчанием — лог просто обрывался на последнем документе. Теперь на переходе «работал → очередь пуста» пишется число обработанных документов и время прохода; в простое строка не повторяется |
| `graph-rag-svc` | Перезапуск сервиса во время сборки графа блокировал кнопку пересборки навсегда: сборка выполняется как задача внутри процесса и рестарт не переживает, а строка прогона оставалась в статусе `running`; `POST /internal/graph/build` отказывает при любом незавершённом прогоне, и снять это из интерфейса было нельзя. При старте такие прогоны теперь помечаются прерванными |
| `db-svc`, схема БД | Админка подключалась суперпользователем контейнера (он же владелец всех объектов), а действий не журналировала: кто удалил строку или файл, установить было нельзя. Теперь у db-svc своя роль без DDL (запись только в `core` и `library`, остальное на чтение, без `password_hash` и `token_hash`), у остальных сервисов права сужены до реально используемых (library-svc — только чтение, ingest-worker — только статусы очереди и чанки, у него своя роль), объекты принадлежат NOLOGIN-роли `app_owner`, пароли ролей берутся из `.env`, а не из SQL. Все изменения пишутся в `audit.db_actions` (кто, когда, что; прежнее и новое значение). Миграция `008_roles_and_audit.sql`, описание — `infra/db/README.md`, проверка — `infra/db/tests/check_roles.sh`. IVHR-18 |

Проверено на живом стеке: сборка `nginx` вместе с фронтендом, отсутствие обхода авторизации
в прод-бандле, сборка `ingest-worker`, отказ `db-svc` стартовать без токена и весь путь входа
в админку. Правки в `library-svc` и `embedding-svc` пока проверены только тем, что сервисы
поднимаются.

### Требуют внимания

| Где | Проблема |
| :-- | :-- |
| `library-svc` | Собственной аутентификации по-прежнему нет: сервис доверяет любому, кто попал в сеть compose. Правильное решение — проверять `X-User-Id` от gateway, как делает `chat-svc` |
| `ingest-worker` | Нет механизма переиндексации, а он теперь нужен регулярно (смена модели эмбеддингов, обновление документов) |
| `embedding-svc` | Модель грузится при импорте: неудача = цикл перезапусков контейнера. Нет healthcheck в compose |
| `db-svc` | Dry-run импорта не проверяет ограничения БД: он останавливается до обращения к базе и валидирует только разбор CSV и сопоставление ссылок. Успешный dry-run поэтому не означает, что импорт пройдёт. Полноценной проверкой был бы прогон в транзакции с `ROLLBACK` |
| `ingest-worker` | Чанкинг теперь по символам, как в ноутбуке (до 1600, overlap до 350). У `multilingual-e5-base` окно 512 токенов: русский чанк в 1600 символов с заголовком может не поместиться целиком, и хвост в эмбеддинг не попадёт. Проверить на корпусе |
| весь стек | **Требуется полная переиндексация.** Модель эмбеддингов заменена на `intfloat/multilingual-e5-base` (768); миграция `011` удаляет старые векторы и возвращает документы в `pending`. Порядок — `../deploy.md`, «Миграция на e5» |
| `db-svc` | Вкладка «Граф» админки по-прежнему обращается к `/api/graph/*`, которые отключены (`404`), — интерфейс нужно почистить |

### По сервисам

- **`graph-rag-svc`** — [§4.1 и §9 README](graph-rag-svc/README.md). Ограничения пайплайна
  ноутбука: устаревшие название и категория документа в индексе до переиндексации, нулевые
  оценки BM25 в кандидатах, токены реранка не входят в `usage`, `FAIL_CLOSED_ON_INJECTION=true`
  теперь отказывает вместо ответа без контекста (нужно согласие владельца). Проблемы графа
  отложены вместе с ним.
- **`chat-svc`** — [§34 README](chat-svc/README.md). JWT проверяет не сам сервис, а gateway;
  CRUD-API нет, всё через WebSocket.
- **`auth-svc`** — [README](auth-svc/README.md). Подтверждение почты, SMTP и шаблоны из
  `core.email_templates` реализованы; сроки жизни токенов и интервал повторной отправки
  настраиваются, Redis используется как дополнительный кэш. Регистрация и повторная отправка
  используют единый сценарий; внутренний `POST /internal/notifications/email-verification`
  доступен только `db-svc` по mTLS. Повторная регистрация не меняет пароль, ссылки одноразовые
  и проверяются в PostgreSQL с блокировкой пользователя (IVHR-54 / IVHR-55).
  Доставка через SMTP стенда требует отдельной проверки с его настройками; инструкция —
  [deploy.md](../deploy.md#обновление-подтверждения-почты-ivhr-54--ivhr-55).
- **`ingest-worker`** — [«Технические проблемы»](ingest-worker/README.md). Нет healthcheck,
  нет retry/backoff, нет лимита размера файла, опрос базы вместо очереди, HTML зависит от
  внешнего преобразования.
- **`library-svc`** — [«Технические проблемы»](library-svc/README.md). Кроме перечисленного
  выше: незащищённый `/library/refresh`, кэш дерева не восстанавливается после неудачного
  старта и не инвалидируется при правках через db-svc, ошибка при стриминге отдаёт битый
  файл со статусом 200.
- **`db-svc`** — [«Технические проблемы»](db-svc/README.md). Кроме авторизации: нет журнала
  действий, подключение админской ролью, токен в `localStorage`, соединение с БД создаётся
  на каждый запрос.
- **`embedding-svc`** — [«Технические проблемы»](embedding-svc/README.md). Модель грузится
  при импорте (падение = цикл перезапусков), нет healthcheck в compose, ошибка в
  `TRUSTED_SERVICE_TOKENS` молча запрещает все вызовы.
- **`frontend`** — [«Технические проблемы»](../main/frontend/README.md). Кроме обхода авторизации:
  слишком агрессивный watchdog стрима (6 секунд), источники ответа не отображаются, хотя
  сервер их уже присылает.

### Открытые вопросы на нашей стороне

Эти пункты касаются только нас — в контракт для соседней команды они намеренно не вынесены,
чтобы не грузить их нашей внутренней кухней.

- **Стыковка краулера.** `services/crawler-svc` написан и загружен, но со схемой не совмещён:
  он объявляет собственную `library.documents` с колонками `url`, `file_hash`, `text_hash` и
  `id SERIAL`, тогда как у нас `id UUID`, `origin_url`, единый `checksum` и обязательные
  `title`, `category`, `source_type`. Его `INSERT ... ON CONFLICT (url)` на нашей схеме
  упадёт. Глубже: он вообще не сохраняет файл — считает хеши и выбрасывает байты, не заполняет
  `library.document_files` и ничего не кладёт в MinIO, поэтому `ingest-worker` такие документы
  не увидит (выборка идёт через соединение с `document_files`). Плюс мелочи: статус успеха у
  него `success` против нашего `indexed`, свои таблицы в `public` вместо именованной схемы,
  а `is_document_url` берёт только `.pdf` и `.docx` — HTML-страниц, которых у нас 37 из 92,
  он не подхватит.
- **Импорт выгрузок обратно.** Экспорт графа и чанков архивом сделан, загрузка — нет. Нужны
  решения: сверка манифеста с принимающим стендом (размерность и модель эмбеддингов), слияние
  против замены, судьба идентификаторов и провенанса, порядок вставки с учётом внешних ключей.
- **Права в БД.** Принудительное разграничение «кто пишет в граф» отпало, потому что UI
  курирования живёт в нашем db-svc. Сейчас это процессная договорённость.
- **Список операций курирования** стоит показать соседней команде до того, как они начнут им
  пользоваться.

## Соглашения

- **Выводы и найденные проблемы фиксируются в README соответствующего сервиса**, а не только
  в переписке. Этот файл — сводка, детали живут в сервисах.
- **Межсервисная аутентификация** везде одинаковая: статических токенов нет, вызывающего
  подтверждает клиентский сертификат (mTLS), а имя из него прокси-сайдкар получателя передаёт
  приложению в `X-Caller-Identity` (верят только от loopback). Режим — `INTERNAL_AUTH_MODE`
  (`mtls` по умолчанию, `insecure` только для отладки без PKI). Подробности — `infra/pki/README.md`.
- **Размерность эмбеддингов** объявляется один раз в `main/.env` (`EMBEDDING_DIM`, сейчас 768) и
  сверяется сервисами при запуске. Смена модели эмбеддингов = переиндексация всех чанков,
  вариантов быстрых ответов и ссылок (и пересборка графа, когда он вернётся).
- **LLM** вызывается только через `llm-proxy`; ключ роутера живёт только в его окружении.
- **Онтология и схема `graph`** — общий контракт двух команд: изменения затрагивают обе
  и требуют согласования.
